# Should the corpus-index overhaul be built in archon-cli?

**Verdict: qualified yes — a hybrid, with a specific split.** Date: 2026-07-29. Repos: incumbent `/home/dalton/projects/claudeflow-testing`, proposal `/home/dalton/projects/archon-cli`.

---

## 1. Recommendation

**Build the store and the claim/clause layer in archon-cli; keep the authoring adapters in Python; do not make archon the producer of `compiled-index.json` in this phase.** The goal — every claim and every clause with a character position, a page, a bbox and an exact-vs-fuzzy verdict — is structurally unreachable in the incumbent: all five parsers in `scripts/compile-corpus-index.py` destroy text offsets in the first executable statement of every function, the artifact format needs ~591x its current payload against a measured loader ceiling of ~25x, and `claudeflow-testing/.archon` is 28,672 bytes and empty. Archon already holds the only substrate that can carry the target — a 987 MB CozoDB with 226 ingested documents, `doc_chunk_blocks{char_start, char_end, page, x0..y1}` populated at 114,612 rows, and a working exact/fuzzy quote locator. But archon has no compiler, no `corpus_*` relations (`grep -rn ':create corpus_' crates/ src/` → empty), no adapters, and a track record that says a single M–L feature costs 15 days and lands incomplete. So the port must be scoped to the half that only archon can host, and the half that is genuinely language-independent — parsing 27 hand-authored entries across seven layouts and 41 CSV dialects — must stay in Python, emitting a typed intermediate that archon imports. That is not a compromise for its own sake: it is what the evidence supports on both sides.

## 2. The case for, ranked by force

**1. The requirement is unreachable in the incumbent, not merely awkward.** `scripts/compile-corpus-index.py` — `parse_table_ontology` (def :195) opens with `re.search` on whole text; `_parse_field_value_ontology` (:292) with `re.split`; `parse_header_ontology` (:513) with `_parse_header_tables`; `parse_cross_pipeline_hooks` (:774) with `re.split`. Seven `.start()` calls exist in 1,412 lines and every one is consumed immediately to slice a section boundary. No character position survives into any record. Archon computes the same positions and already uses them: `crates/archon-docs/src/quote_verify.rs:162-166` computes `(a,b)`, `:297-311` derives chunk-local `(lo,hi)`, `:321-339` narrows the page, `:343-361` narrows the bbox. This is the whole argument in one line: one repo throws offsets away by construction; the other computes them and merely lacks a struct field to keep them.

**2. Only one repo has a corpus to ground against.** `archon docs status` → 227 sources / 226 ingested / 17,824 chunks / 17,744 pages / 17,824 indexed. Verified live: `archon docs verify-quote "the soul is in a way all existing things"` → EXACT, p.48, bbox `[66,327,360,368]`, locator `431b1 (Bekker)`, with fuzzy 72%/68% runners-up on unrelated books correctly ranked below. `du -sh /home/dalton/projects/claudeflow-testing/.archon` → 32K, empty. There is no version of this overhaul that runs in claudeflow-testing without first re-ingesting 226 PDFs — by a wide margin the largest single item on either side of the ledger.

**3. The consumer half is already written, tested and wired.** `crates/archon-evidence/src/index.rs` is 977 lines (674 impl + 303 test) implementing greedy longest-match canonical-term expansion (`:346-415`), tension-pole surfacing that resolves qualified poles through a surface map (`:418-470`, whose own doc comment records that string equality silently missed ~81% of edges), and author-anchored owning-work routing (`:475-568`), with 14 tests. Measured counterfactual on the same query, only `--index` removed: without it, the top-2 for "poor in world" are OCR chunks at relevance 0.4747/0.4668; with it, Heidegger FCM chunks at 0.8039/0.7849, `is_primary: true`. Zero tests in claudeflow-testing reference its three index modules and no CI job references the compiler or the artifact.

**4. Cozo has no `ALTER`, and the claim relations are empty today.** `crates/archon-knowledge/src/schema.rs` `run_create` (:45-66) only swallows "already exists"; there is no column-add path in the workspace. `kb_claims` (:86-96) has nine columns and none of char_start/char_end/page/bbox/locator/match_kind — and it currently holds zero rows in the live store. Getting the column set right is free now and means create-new-copy-swap over 450,000 rows later. This is a timing argument that favours deciding now, in archon.

**5. Both copies of the index already exist and one has already drifted, silently.** archon `index/compiled-index.json` = 643,548 bytes, built 2026-07-16, 670 nodes / 1663 terms. Incumbent `corpus/index/compiled-index.json` = 666,303 bytes, built 2026-07-29 (today), 701 / 1722. archon's retrieval, curation and drafting paths (`crates/archon-evidence/src/index.rs:24`, consumed at `src/command/evidence.rs:154,:218`, `curate.rs:341,:624`, `draft.rs:263`) are routing off a 13-day-old artifact right now, and four of those five sites swallow load failure with `.ok()`. Whatever is decided, the two-copy arrangement must end — and that is itself a reason to settle ownership deliberately rather than let it drift further.

**6. The dependencies for the Rust side are already vendored.** `Cargo.toml:57` pulldown-cmark 0.12, `:50` csv 1, `:48` jsonschema 0.28 (already in use at `crates/archon-core/src/schema_validation.rs`). No new crates, no new build risk.

## 4. What refuted

Sixteen of forty load-bearing claims failed verification. The five that change the decision:

**Archon's retrieval provenance is partly a tautology.** `crates/archon-evidence/src/lib.rs:361` passes the retrieved chunk's *own content* to `find_fragment_bboxes`, which searches a concatenation of that document's chunks (`quote_verify.rs:149`, `:533-543`). A chunk is by construction a substring of that concatenation, so the exact branch is structurally guaranteed. Measured: `match_kind: "exact"`, `similarity: 1.000` in 57/57 candidates with provenance, zero fuzzy. `"exact"` in `evidence find` output is a constant, not a measurement. The capability that genuinely discriminates — returning only fuzzy 0.741/0.704 for the fabricated ped-sec-29 quotation — is `docs verify-quote` with a user-supplied string, a different entry point.

**bbox coverage is 68%, not universal.** Across 60 candidates over five queries: 3 returned no provenance, 16 more returned `"bbox": null` — 19/60 (32%). Split is by ingest path: `chunk-doc-*` (Marker) has bbox, `chunk-pdf-image-ocr-*` does not. Independently, `doc_chunk_spatial` holds 11,311 rows against 17,824 chunks — 36.5% of chunks have no spatial row at all. And `locator` was null in 16 of 18 fragments in the limit-20 run. Any gate keyed on bbox presence fails closed on a third of the corpus.

**The draft-time verification gate is on one of five entry points, and not the one named.** `preflight_draft_inputs` has exactly one caller: `src/command/draft.rs:789`, inside `DraftHandler::execute`, the TUI `/draft` slash command (registered `src/command/registry/default.rs:69`). The CLI `archon draft` dispatches at `src/main_dispatch.rs:82` to `handle_draft_command`, which calls `orchestrator::run` at `draft.rs:116` with no preflight — and the gated TUI path then *shells out to the ungated one* (`src/command/slash.rs:210`). `archon-fcdp run`, the wizard, and `evidence curate --draft` are all ungated. Root cause is structural, confirmed this session: `crates/archon-draft/Cargo.toml` has no archon-docs or archon-evidence dependency. The engine cannot verify anything.

**"FCDP has no implementation in claudeflow-testing" is overstated, and the search that produced it could not have found the counter-evidence.** `FCDP-DRAFTING-PROTOCOL.md` is 199 lines at the incumbent repo root and is the normative protocol; `scripts/analyze-lanham.ts` (131 lines) is the G-A style gate over a 933-line analyzer. The claim's `find -name "*.py"` was structurally incapable of matching a `.ts` file. The correct finding is *fragile and untracked* (all three are untracked in git), not absent — which is a different and arguably stronger argument, but not the one that was made.

**Cozo scale numbers measured the wrong layer.** The 80 ms "FTS scan" was `select count(*)` over a key range, resolved as a covering-index search; actually reading the values costs 2,543.7 ms, 32x worse. All probes hit raw SQLite, bypassing MessagePack decode, DataValue materialization and Datalog execution. Measured against the real engine: `docs status` 1.14 s, `verify-quote` 3.34-5.22 s exact and 12.12 s for a not-found quote. **This is the single most consequential number in the review**: at 45,000 claims, one `verify-quote` per claim is 42.5 h serial best case and 151 h for the not-found case. The design implication is decisive and is covered in §6.

**Also corrected:** archon's `index/` tree is committed under `e910839c`, whose own message reads "a WORKING DATA ASSET, not part of the shipped code: it MUST be wiped before any upstream PR." It is a transport copy scheduled for deletion, not a home. And archon's 1,730 tracked index files have zero readers — an exhaustive grep for `units/|_synthesis|edges\.csv|book-level-ontology` across `crates/` and `src/` returns only unrelated workflow test fixtures. Presence is not wiring; the adapter is exactly as unwritten in archon as in the incumbent.

## 6. The migration shape

**Does archon become the producer, with `compiled-index.json` as a legacy view? Not in this phase — and this is a deliberate reversal of the obvious plan.** The emitter is ~350-450 Rust lines plus bug-compatibility for two defects a clean implementation would naturally fix, and it buys nothing the Python compiler does not already produce. The problem it is meant to solve — two drifting copies — is solved for ~30-60 lines by deleting `archon-cli/index/` (which its own commit message schedules for deletion) and adding a `--corpus-index-root` flag / `ARCHON_INDEX_PATH` production reader so archon reads `/home/dalton/projects/claudeflow-testing/corpus/index/compiled-index.json` in place. The loader is already path-generic at `index.rs:266`. Do the cheap fix now; revisit the emitter only when the Python compiler is genuinely retired.

**For the record, the contract if and when it is built** (measured over the live artifact, all uniform): exactly one key order per record type — `ontologyNodes` = `name, greek, transliteration, translation, definition, type, units, text, aliases, centralityTier`; `crossPipelineHooks` = `id, sourceText, sourceConcept, targetText, targetConcept, title, bridge, relevance, tag`; `tensionEdges` = `id, text, nodeA, nodeB, dependencyRelation, conflictRelation, description, units`. All scalars strings, no nulls, `units`/`aliases` always `list[str]`. `canonicalTerms` sorted `(-len, lower)` with zero duplicates. `ontologyNodes` emitted in owning-entry order per the `TEXT_DIRS` declaration order (`compile-corpus-index.py:37-128`), verified as 28 contiguous non-interleaved runs — not derivable from record content, so it must ship as a data table. Three bug-compatibility requirements: preserve the 31 empty `targetConcept` values (filling them changes bridge selection on every run), preserve `INTERP-med` (normalizing to `INTERP-medium` re-ranks 8 hooks at `cross-author-utils.ts:489-490`), and guarantee every node has a non-empty `name` (`scripts/merge-reasoning-edges.py:47` uses a bare subscript and is the only hard-failing consumer). Seven `catch` blocks plus one bare `except: pass` mean every other failure is silent. Frame the legacy view permanently as a frozen compatibility shim at roughly today's size — treating it as the growth path is the one framing error that invalidates the whole plan, given the ~25x loader ceiling against a ~591x target.

**Does the corpus tree move? No — it is read in place across the repo boundary, and archon's fork is deleted.** claudeflow-testing is where authoring happens (7 modified index files right now) and where the compiler lives. archon's copy is 26 files behind, missing three whole entries, and has 1,730 files with zero readers. Deleting it removes a fidelity liability. Separately and urgently: `git add` the 1,522 untracked files in `corpus/index` — they are unignored, merely never staged, and are the only copy of the hand-authored asset.

**The split.** Python owns parse-and-normalize and emits a *typed intermediate* (one JSON record stream with stable ids, per-entry provenance, and a schema file) rather than the lossy compiled artifact. Rust owns the store, the claim/clause relations, grounding, verification and query. This is exactly what the 231-agent review recommended — keep the five markdown parsers as adapters — and what the migration spec's own §0 demands: import from source files, never from `compiled-index.json`, which carries 837 of the tree's 32,677 machine-readable records (2.6%) and strips every id and locus.

**The grounding design note that saves 100+ hours.** Do *not* ground claims by calling `find_fragment_bboxes` with claim text. Measured: 3.34-5.22 s exact, 12.12 s not-found, because `quote_verify.rs:139-149` reconstructs up to 8 candidate documents and runs a per-chunk Sellers alignment. At 45,000 claims that is 42.5-151 h serial. A claim extracted from a known chunk already knows its `chunk_id` and its local char range; grounding is then a direct `(chunk_id, char range) → doc_chunk_blocks` lookup. Reserve `find_fragment_bboxes` for the adversarial case — checking a *supplied* quotation, where the 12 s not-found path is exactly the behaviour you want.

**Dual-run/diff period.** Two weeks minimum, and it must run across separate process invocations, never in-process: `_hooksDerivationDone` (`cross-author-utils.ts:56`, set at `:351`, never reset) mutates the shared mtime-keyed cache and would corrupt an in-process artifact swap. Prerequisite: freeze a baseline. `corpus/index/compiled-index.json` is currently dirty (+589/−61) and `compile-corpus-index.py` is uncommitted (+15); until both land, "the incumbent's output" is not a fixed object and no diff is meaningful. The differ is ~150 Python lines (array counts, key-order tuples, `canonicalTerms` sortedness and set equality, node-name symmetric difference, empty-`targetConcept` count, tag histogram) and it must write to stderr, because nothing else in the incumbent ever does.

**The very first commit, and what it proves.** Not schema. `scripts/ingest/run_ingest.py:365`, `scripts/ingest/run_ingest_phase2.py:978`, `scripts/ingest/parallel_ingest.py:69` — add `"index"` to each `SKIP_DIRS` set (verified this session: all three read `{".extracted_media", "__pycache__", "node_modules", ".git", ".ingest_cache"}`; note the paths are under `scripts/ingest/`, not `scripts/`, correcting the review's citation). Three tokens. It stops 518 of 522 index manifest records re-embedding into the live corpus on the next routine ingest. It proves nothing architectural and it is still the right first commit, because it stops active corruption of the asset the whole overhaul is about.

## 7. The cheapest thing that could possibly work

**The opponent is right that days, not months, buys most of the near-term value — and wrong about which days.** Assessing the specific proposal: the two-field char-offset change plus a match_kind-gated checker.

**The char-offset change is real but inert this week, and should be last of the cheap items, not first.** It is ~10 lines and the values are already bound two lines above the struct literal (`quote_verify.rs:374`, literal at `:405-411`). But nothing consumes offsets today: `CuratedQuote` (`pack.rs:20-41`) has no slot, `QuoteEntry` (`draft/lib.rs:169-173`) has no slot, and `archon-draft` cannot even call `quote_verify` — confirmed empty this session. Adding two fields that flow nowhere is a down-payment, not a delivery. Do it, but do it as part of the plumbing commit that gives them a consumer.

**The match_kind gate is mis-scoped: it already exists and is correct.** `verify.rs:88-101` `blocking()` matches `Missing | Drift | NearVerbatim | WrongSource` so only `Exact` passes, with six tests. The defect is not a missing match arm — it is that the gate is wired into one of five entry points and the engine has no corpus dependency. Fixing that is ~60-120 lines and is genuinely the highest-value cheap item in archon, because it closes the gap that produced the ped-sec-29 fabricated quotation. While there, close the swallowed `Err` at `draft.rs:1050-1053`, where a Cozo failure yields a clean warning-free pass, and stop keying anything on `docs.rs:141` `"found": !locations.is_empty()` — with `REPORT_FLOOR = 0.60` a fabrication returns `found: true`.

**The two Python fixes the opponent lists are both confirmed and both underrated.** The `elif` reorder at `compile-corpus-index.py:718-721` is verified unreachable: `elif current_key and stripped:` catches every non-empty line once any field key is set, so the `break` at `:721` can never fire and the last field absorbs the remainder of the file — the mechanism behind the 10,009-character `centralityTier` with 973 garbage tokens in its units array. Four lines. And `SKIP_DIRS` is confirmed above.

**Ranked list for the next week, all reversible, ~1-2 days total:**

1. `SKIP_DIRS += "index"` in the three ingest scripts — 3 tokens; stops live corpus pollution.
2. `compile-corpus-index.py:718-721` elif reorder — 4 lines; stops field-spill corruption at source.
3. `git add corpus/index` (1,522 untracked files) + commit the dirty artifact and compiler — establishes the frozen baseline every later diff depends on, and removes a single-disk data-loss exposure.
4. Delete `archon-cli/index/`, add production `ARCHON_INDEX_PATH` / `--corpus-index-root` — ~30-60 lines; ends the drift permanently and makes archon read today's artifact instead of a 13-day-old one.
5. Fix `ig-10-incorporation.json` (verified invalid: `Expecting ',' delimiter: line 155 column 3`) — minutes; one file currently blocks the Calleja monograph for any strict importer.
6. Move the verify gate into `handle_draft_command` + close the `Err` swallow — ~60-120 lines.
7. `char_start`/`char_end` on `QuoteFragment` and its two JSON emitters — ~10 lines, as plumbing for item 6.

Items 1, 2, 3 and 5 all live in the incumbent. That is the honest shape of the near term: **the cheapest high-value week is mostly Python, and it is not the port.**

**Two conditions on P2 and beyond.** First, land the 186 unpushed commits, or at minimum push them somewhere — the entire archon-evidence crate, all six critical fixes and the reranker work exist only on this WSL box, and `--corpus-index-root` plus the claim layer would add to that pile. Second, point CI at the working branch or merge to `main`; building a 14-relation subsystem on a branch CI has never seen is how the incumbent reached its current state, and the blocking `cargo fmt` gate is red today.

**Two risks to carry forward explicitly.** `doc_chunk_blocks` columns are named `char_start`/`char_end` but the doc comment at `schema.rs:189-192` says they are *byte* ranges, and `local_span_in_chunk` returns bytes, while `quote_verify.rs:150` normalizes into a *char* vector — a claim record that inherits the name without the semantics will mis-slice every Greek, German and accented span, which is precisely this corpus. And corpus text quality, not architecture, is the binding constraint on 450,000 clauses: live retrieval returns `pnractical`, `consiaered in 1tsely`, `Involvernent`. A chunk-level system tolerates a few corrupted tokens; a clause-level system indexes them as claims.
