## 7. Scalability ceiling — the section that decides the programme

### Recommendation: **REPLACE the parse-and-emit layer. HARDEN the loaders, the orchestration, and the reasoner's skeleton.**

I am not hedging: the split is the answer, and each half is argued below.

**REPLACE — `compile-corpus-index.py`'s parse and emit layers (~1,100 of 1,412 lines), `normalize-edges.py` (306 lines, entire), `merge-reasoning-edges.py` (237 lines, entire), and the TS matching/rendering layer (`cross-author-utils.ts:408-614` + `corpus-index-provider.ts:79-197`, ~600 lines).**

Four pieces of evidence, in order of force.

1. **The structured data already exists and the compiler ignores it.** `grep -c "ontology.json"` over 1,412 lines returns **0**, while **12 `*-ontology.json` files sit in the same directories the compiler scrapes**. *Heidegger and Rhetoric*'s is 56,912 bytes with structured `canonical_nodes` carrying `contributors` and `cross_pipeline_links`, `contested_concepts` with per-contributor readings, and a `tension_summary` — precisely the fields the markdown scrape loses. **The pipeline is doing the hardest possible job — recovering structure from prose — when the structure is on disk in the same folder.** Hardening a scraper that competes with a structured twin is work spent to reach a worse result. This single fact decides the harden-or-replace question.

2. **The defect density is architectural, not incidental.** In one 500-line window: 2 corrupt shipped nodes, 17+ silent-discard branches, 4 dead/unreachable blocks, 3 latent silent-row-deletion paths, zero tests. The bugs are not independent — they descend from one decision, to parse a structured document with line-at-a-time regex and mutable flags. The *same* unbounded-section bug exists independently in **two** parsers (`:308` and `:718`), which is what happens when three markdown dialects get three hand-rolled scanners instead of one grammar. Fixing `:718` fixes 2 nodes; it does not make `:539-540`, `:558`, `:606`, `:611-614` or the absent provenance any less true.

3. **The schema is a dead end for the stated goal, and that is not tunable.** A claim record is `(text, source_path, heading_path, line_start, line_end, char_start, char_end, type, subject, polarity, evidence_refs)`. The emitted dict has ten flat fields and **not one is an identity or an anchor**. Adding provenance is not a schema addition — it requires the parsers to track offsets, which none of them do, at any point. Meanwhile the corpus already *contains* claim-level records: `metaphysics-ontology.md` `## 3. Key Positions` is 14 numbered claims each with a Bekker locus and a status, and this code absorbs all fourteen into the ὄρεξις node's `fields` dict as keys `'1'..'14'` and drops them at `:379-390`. **The data exists; the schema has nowhere to put it.** Likewise the compiler demonstrably parses Rickert's tension structure (`node a`, `node b`, `dependency edge`, `conflict edge`, `synthesis`) and then throws 732 bytes away in the same function call, because the return dict has no slot.

4. **Nothing depends on current behaviour, so the replacement cost ≈ the hardening cost.** `grep -rln` over `tests/` finds **zero** tests referencing any of the three TS modules; the sole check is `scripts/verify-hardening.ts`, in neither CI nor `package.json`, whose one bridge assertion passes only because its query happens to contain a literal German word sitting in a `targetConcept`. And the always-true `t.includes('')` at `cross-author-utils.ts:474` means **the bridge feature has never actually worked on this corpus** — there is no working behaviour to preserve, only the appearance of one.

**HARDEN — `jsonl-loaders.ts` (310 lines), `loadManifestCanonicals` (`cross-author-utils.ts:77-173`), `god_learn.py`'s orchestration, `reason_over_knowledge.py`'s pair machinery, and `compile-corpus-index.py:195-1025` as adapters.**

This code is genuinely good and rewriting it would be pure risk. The mtime-cache pattern is right; the Zod boundary for KUs and edges is right (`types.ts:93-134` even reports per-record failures with offending field paths); the dropped-line counters at `jsonl-loaders.ts:66-68` and `:103-105` are exactly the observability the rest of the system lacks. The HTTP wiring to the embedding API and Chroma (`smart-retrieval-layer.ts:898-945`) is correct, the `kind: 'query'` asymmetry fix at `:901` was hard-won, and the rerank integration (`:1220-1286`) is well-structured with an AbortController timeout, index validation, and preserved `retrievalScore`. The five parsers at `:195-1025` handle four genuinely different markdown dialects that real analysts produced over a year and they *work* (771 nodes, zero exceptions) — even the one that fails (RDR2 Secondary's `- **Name** — gloss — units · Tier` bullets → 0 nodes) fails by omission, not corruption. **Lift them out as per-format adapters; do not rewrite them.**

**The smallest replacement that preserves the authored content.** The corpus under `corpus/index` — 30.9 MB, 1,848 files, 240 CSVs, 22 manifests, 12 structured ontology JSONs — is the real asset and must not be touched. Concretely:

1. **Invert the source of truth.** Read `*-ontology.json` where present; treat markdown as rendering. Make a missing JSON an *error*, not a silent fallback. This immediately recovers `contributors`, `cross_pipeline_links`, `contested_concepts` and `tension_summary` that the scrape currently loses.
2. **Lift `:195-1025` out as adapters** (they are already nearly pure functions of `(text, label)`), giving each an offset cursor and an `extra` passthrough for unrecognised keys.
3. **Rewrite `:1181-1412`** (~250 lines) as a schema-first loader: discover entries from `_synthesis/manifest.json` (22 exist), validate every record, assign stable ids with `(source_path, heading_path, line span, char span)`, refuse to publish on zero-node parses or unexplained count drops, and exit non-zero.
4. **Shard the artifact per entry** with a manifest; move to SQLite/FTS5 (the repo's existing idiom) for anything claim-level, with an inverted term→claim index and a concept→edge adjacency map so boosting becomes O(terms in chunk) rather than O(total claims).
5. **Add a CSV adapter** so the 240 files / 20,610 curated edge rows — the densest, most locus-bearing content in the index, currently at 0% runtime reachability — become first-class records.

Estimate: **2–4 weeks**, and it *deletes* more of `compile-corpus-index.py` than it ports. Against that, hardening the CRITICAL/HIGH list alone is ~15 structural items requiring provenance threading through five parsers, a markdown AST to replace `:244-289`/`:335-344`/`:701-724`, a claim/clause record model, and a validation harness — a **larger** diff that arrives without the provenance the current design has no slot for.

**One decisive piece of context.** The docstring at `:14-15` has promised stderr warnings since the file was written, and the mechanism emits **nothing at all** on the live corpus. The design has been failing silently for its entire history with zero observability, and every number in this report had to be recovered by re-running the parsers by hand. That is not a system to tune. **Verdict: the markdown/JSON corpus under `corpus/index` is an excellent foundation. `scripts/compile-corpus-index.py`'s parse-and-emit layer and the TS matching layer are obstacles and should be replaced.**
