Paraguay Widget Forensics The widget is damaged. The damage is not what stops it playing.

A structural comparison of the Cataract Operations — Paraguay video widget against three working peers and against a second copy of the whole project, read directly out of the serialized .uasset package tables.

Verdict · revised

The blueprint defects catalogued here are real, but they are not the cause of the failure. A byte-identical copy of this widget plays correctly in a shipped Windows package, which rules the graph damage out as the operative fault.

The first version of this report concluded that dangling variable references stop the Blueprint compiling and therefore stop the graph running. That inference was wrong in one specific way: K2Node_* nodes are editor-only and are stripped at cook, so a packaged build executes the bytecode serialized into the BlueprintGeneratedClass, not the graph. Dangling editor-graph references break an editor compile; a cooked build runs the last bytecode that compiled cleanly. See §06.

The live hypothesis is now platform, not blueprint: no media-player override exists on any media asset in either project today, and the Mac needs one to decode these streams. That is a Mac-only, media-only regression — the right shape for "identical widget, works on Windows, dead on Mac." It is not yet proven; §05 names the test that settles it.

01What is actually wired into the level

Worth establishing first, because the Paraguay folder holds four widget variants and four screen variants, and only one pair is live.

Hospital_Client is a World Partition map — its actors live in __ExternalActors__, which is why the .umap itself names none of them. Across its 4,520 external actors there is exactly one Paraguay screen instance, the same count as each of the other ten procedures:

The screen actor is not the problem. BP_SC_CAT_PARA correctly drives all four Paraguay media players and all four materials. The widget it hosts only knows about two of them.

03The defects — real, catalogued, not fatal

Everything below is read from the package name, import and export tables. It is all still true, and all still present in both projects. What has changed is its status: this is technical debt and latent risk, not the reported fault.

E1

The POV media players were dropped from the widget

Four Paraguay media players exist on disk, each with a matching media texture and material. The screen actor references all four. The live widget hard-references only two — and both working Paraguay siblings reference all four.

The rework added quality selection — Button_1080_High, Button_1080_Low, Button_4K appear throughout the name table and in 80 compiled event names. The widget tree contains 50 buttons and not one carries a quality name. The components were removed; the graph nodes reading them were not.

3,212 export objects against 533 for the UCI widget, from a 5.9 MB package where every other widget in the folder sits between 660 KB and 915 KB. Button count is unchanged at 50 — the growth is entirely graph nodes, from hand-duplicating a play block per video × per resolution.

E5

Every button is bound twice, by two different mechanisms

The working widgets bind clicks one way only — designer-bound component events. The live Paraguay widget keeps all 27 of those and adds 80 runtime Bind Event to OnClicked nodes. Runtime binding adds to a multicast delegate rather than replacing, so a click dispatches to both handlers.

E6

128 media-opened handlers are bound and never released

The OnMediaOpened → Play idiom is duplicated across every video-and-quality combination. Media players are project assets, not per-instance objects, so these handlers accumulate on shared state. There is not one RemoveDelegate or ClearDelegate node anywhere in the folder — the working widgets get away with it because they bind 7 and 32 times, at construction.

05The live hypothesis: the missing player override

Mac's default media backend cannot decode this content; a per-asset player override pointing at ElectraPlayer is what made Mac playback work during the July packaging session. That override is not on disk today.

Searching both projects for the property that carries it returns nothing:

Player overrides found in Content/Media:
Windows project  →  0 assets containing PlatformPlayerNames or ElectraPlayer
Mac project  →  0 assets containing PlatformPlayerNames or ElectraPlayer
Project Config/*.ini media settings, either side  →  none

Parsing BilatScar_360.uasset — the first asset the July session overrode, and the one whose Electra playback is recorded in the logs — both copies carry the same 13-entry name table, with no override property in either. An override would have to appear there as a name.

The stream sources were touched on the Mac: 442 of 444 differ between the two projects. But the differences are small and sit outside the name table — 69 differing bytes for BilatScar_360, with 32 bytes inserted in the thumbnail/GUID region and byte-identical tails. The assets were re-saved. No override property persisted.

Whether the bulk pass never wrote the property or something reverted it later cannot be determined from disk state alone. Either way, if the override is what made Mac playback work, the Mac project does not have it now.

How this would produce both symptoms

Dead video follows directly. The stuck menu follows only if the return-to-menu path hangs off the media callbacks — and the widget binds OnMediaOpened 128 times (E6), so if the source never opens, none of those continuations run. That second step is consistent with the evidence but is inference, not proof.

The test that settles it

On the Mac, re-run set_electra_override.py, then open one affected asset and confirm Player Overrides actually shows Mac → ElectraPlayer after saving. If the property does not persist across a save, that is the bug. If it persists and Paraguay then plays, the hypothesis is confirmed and the graph defects stay on the debt list.

06Corrections to revision 1

Two errors, both caught by evidence rather than review

The verdict was wrong. Revision 1 concluded that Button_4K and MP_360_POV_CAT_PARA dangling references stop the Blueprint compiling and therefore stop the graph running, and that this single fact explained both symptoms. The operator's Windows package test disproves it: identical bytes, correct playback. The flaw in the reasoning is that K2Node_* objects are editor-only and stripped at cook, so a packaged build never executes the graph — it executes serialized bytecode. Dangling editor-graph references are an editor-compile problem. Revision 1 treated an editor-side symptom as a runtime cause.

An earlier method artifact. A first pass reported dozens of broken asset references across every widget including the working ones. UE encodes a trailing _<digits> as a separate FName number, so the name table stores CAT_UCI_02_LASER for the asset CAT_UCI_02_LASER_360. Corrected for that, genuinely broken references are zero — which is what E7 reports.

Still not verified. No Blueprint has been opened in the editor. The Python scripting plugin is not enabled or built in this project, and enabling it means editing awsTutorial.uproject and rebuilding the editor target — a project change not made unasked. Reading the Compiler Results panel on BP_WG_CAT_PARA would confirm whether the editor-side compile errors exist; that is now a debt question, not the fault line.

07What to do next

First

Restore the Mac player overrides and retest

Re-apply the Mac → ElectraPlayer override to the stream sources and verify it survives a save by reopening one asset. Then run Paraguay on the Mac. This is the cheapest action with the highest information yield: it either fixes the reported fault or eliminates the leading hypothesis.

Cost: minutes. Confirms or kills the platform hypothesis outright.

Then, separately

Treat the widget damage as debt, on its own schedule

E1–E6 are real and survive a Windows cook, which makes them latent rather than urgent. When they are addressed, start from BP_WG_CAT_PARAOG — same 50-button, 2-switcher layout, all four media players, zero dangling reads, same binding architecture as every widget that works — and add quality selection as data rather than as 208 duplicated custom events. Bind OnMediaOpened once at Construct. Pick one binding mechanism and do not mix them.

Cost: a session. Do not bundle this with the playback fix — changing both at once destroys the ability to attribute the result.

Independently: the three dead variants — BP_WG_CAT_PARA_V2, BP_SC_CAT_PARA_V3, and the _Test pair — are unreferenced by any map and worth deleting once Paraguay is working, so the next person does not have to work out which of four widgets is live.
