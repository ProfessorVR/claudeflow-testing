# ICP (Interactive Composition Pipeline) — Interactive Drafting Process: Technical Analysis & Enhancement Report

**Date:** 2026-07-10 · **Audience:** author (review), then Perplexity Deep Research API · **Scope:** the god-agent Interactive Composition Pipeline (`src/god-agent/core/composition`), its two dashboards, and the corpus ingestion + compiled research index.

**Purpose.** Understand ICP's *interactive, step-by-step* drafting process end-to-end — the functions and how each step builds on prior work to culminate in a final, cited draft — as source material for improving a separate interactive drafting protocol (the archon `/draft` wizard). §§1–6 analyze ICP as-is; §7 analyzes how the newer verbatim ingestion + compiled index would upgrade its source-finding and verification.

**Method.** Two multi-agent workflows over the live source tree, each with a line-level adversarial verification pass. Workflow 1 (§§1–6, closing fidelity note): 10 parallel subsystem extractors → synthesis → 3 verifiers (stage-order/IO, interactive-layer, completeness). Workflow 2 (§7): 3 extractors (verbatim ingestion / compiled index / ICP retrieval-verify seam) → synthesis → 2 verifiers. Where verification corrected the synthesis, the corrected fact is stated as fact and flagged inline; unresolved conflicts are presented both ways. Claims are anchored to exact `file:line` where possible.

**Key takeaways (read these first):**
1. **The name oversells the engine.** `ICPOrchestrator.run()` executes its 11 stages *autonomously, once, with no synchronous human pause and no revise/retry loop.* All genuine interactivity lives at the dashboard/route boundary (verify, patch, bind, regenerate, feedback, export). A ported protocol should decide deliberately where its human gates sit.
2. **Shipped ≠ designed — and the gap is the useful signal.** The shipped Dashboard V2 only ever drives the lean `from-evidence` one-shot path; the elaborate claim→atom→binding→stress→plan→ledger→manifest scaffolding is **not exercised by the shipped UI** unless `mode:'full'` is called out-of-band. Several marquee mechanisms are *latent* (defined but unwired): the inline-validation retry loop, the OCR-staleness engine + circuit breaker, the canonical-registry snapshot, and (on the full path) the corpus-constraint that gates citation enforcement. This tells you which ideas are proven vs. aspirational before you port them.
3. **What actually carries quality today:** the human evidence-review gate + `CitationEnforcer` (auto-correct, quotation-similarity 0.70) — because the auto-verifier, as wired, *self-verifies* (no clean text is supplied, so quotes match against themselves) and the Quality Gauntlet is known-degraded (0.5 default per stage).
4. **Highest-value upgrade (your ingestion + index).** The single richest seam: verbatim + bbox provenance already sits in `ContextChunk.metadata` (`bboxes`, `source_method`, `clean_sha256`) but is **dropped at `extractSpansFromChunk`** and never reaches `QuoteSpan`; ICP's `source_anchor` is only a synthetic `p. N` string. Propagating real bbox/verbatim provenance + serving canonical `clean_text` to the verifier, plus wiring the compiled index's 1,442 `canonicalTerms`/author-routing into query building (today just a flat 0.10 boost deep in `SmartRetrievalLayer`), would enable deterministic exact-verbatim citations and let the auto-verify threshold climb from 0.65 back toward 0.85 for high-fidelity sources. See §7.
5. **§5 is the portable menu.** The Portable Feature Inventory lists ~35 discrete mechanisms (with the stage they live in and why they help) as candidates for the archon `/draft` protocol, each flagged for whether it is live or latent in the shipped build.

## 1. OVERVIEW

The **Interactive Composition Pipeline (ICP)** is a corpus-grounded academic drafting system. It converts a raw user prompt into a cited draft plus a reproducibility package by moving evidence through a fixed sequence of stages in which *each stage's output is the next stage's input*, all threaded through a single mutable state object, `ICPSession`.

### 1.1 The two layers: ENGINE vs. DASHBOARD

ICP is split into two cooperating layers.

**The pipeline ENGINE (orchestrator).** `ICPOrchestrator.run(userPrompt, sourceScope, sourcePriority?)` in `src/god-agent/core/composition/icp-orchestrator.ts` (entry point ~line 204) executes an 11-stage linear pipeline. Its sub-orchestrators — decomposer, faceted retrieval, quote ranker, auto-verifier, claim provider, atom binder, stress tester, generator, contract builder, manifest builder — are constructed once (lines 178–190) and reused across runs. Cross-run state lives on three private fields, `corpusConstraint`, `retrievedChunks`, and `stylePromptCache` (lines 170–172); per-run state lives entirely on a single `session: ICPSession` created at line 245 by `createICPSession`. Every later stage reads prior work through `session.*`. **Critically, `run()` executes each stage exactly once and autonomously — it contains no synchronous human pause and no revise/retry loop** (see §6).

**The interactive DASHBOARD.** Two browser panels expose the engine step by step: a modern **Dashboard V2** (`observability/dashboard/icp-panel-v2.js`, a 4-panel depth-mode UX) and a **legacy/Full workbench** (`observability/dashboard/icp-panel.js`, ~2,537 lines, a 13-panel surface). Both talk to the engine through an HTTP contract in `observability/icp-api-routes.ts` (`createICPRouter`, mounted at `/api/icp`). Sessions live in a module-level in-memory `Map<string, ICPSession>`; `serializeSession()` is the canonical JSON wire shape (Maps and Sets flattened).

The interactivity is realized **at the dashboard/route boundary, not inside `run()`**. The dashboard turns the engine's linear stages into an event-driven state machine whose transitions are user button-clicks, inserting human gates (evidence review, binding, quality-gate override, export) between engine calls. Inside the engine itself, the only surviving self-correcting loop in the shipped construction is `CitationEnforcer`'s auto-correct pass; the per-paragraph inline-validation retry loop that the design describes is defined in code but **never wired** (see §1.4 and §6).

### 1.2 Depth modes

Dashboard V2 offers three **depth modes** that change *the process*, not the panels (chosen by radio cards, persisted to `localStorage`):

- **Express** — auto-verify and skip human review; walks prompt → export in one click.
- **Standard** — "Review evidence before generating"; the user manually gates at the Evidence panel.
- **Full** — Standard plus an Advanced Diagnostics drawer (binding, stress-test, planner, heatmap, diagnostics tabs).

### 1.3 Two generation entry paths

The engine can be entered two ways via `POST /adapter/generate/:id { mode }`:

- **`mode:'full'`** → `orchestrator.run()` → the whole 11-stage pipeline (populates atoms, bindings, plan, stress test, ledger, manifest).
- **`mode:'from-evidence'`** → a leaner local helper, `generateFromEvidence(session, router, SmartRetrievalLayer)` (api-routes ~line 1507), that generates directly from the *user-reviewed verified evidence set* using the gold-standard prompt builder plus a fixed quality-gate cascade (§2.12).

**Resolved (was a conflict in the synthesis).** The `design-docs` brief claimed Express maps to `mode:'full'` and Standard/Full to `mode:'from-evidence'`. Reading the actual `icp-panel-v2.js` shows that **both Express and Standard/Full call `v2GenerateFromEvidence()` (`mode:'from-evidence'`)**, and that `v2GenerateFull()` (`mode:'full'`) is defined but **wired to no UI control**. Source verification of `generateFromEvidence` (icp-api-routes.ts:1561–1577) further shows it is a **single one-shot `router.call()`** — there is no multi-step or rolling-context work in it. Conclusion: the shipped V2 UI only ever drives `from-evidence`; the difference between Express and Standard is solely whether the human evidence-review gate is skipped. The "Express → full orchestrator" mapping is unrealized design intent, and the elaborate 11-stage argument scaffolding (atoms/bindings/stress/plan/ledger/manifest) is **not exercised by the shipped V2 flow at all** unless a caller invokes `mode:'full'` directly.

### 1.4 Core quality philosophy

The engine encodes a small number of load-bearing quality principles. Two of them are undercut by how the shipped build is actually wired; those caveats are stated here and detailed in §6.

1. **Closed-book corpus grounding.** The LLM may quote and cite *only* from retrieved corpus chunks and may *never* introduce authors absent from the corpus. This is enforced in the decomposition system prompt, the claim prompt (`buildClaimPrompt`), and the per-paragraph generation prompt (`constrained-generator.ts`), which explicitly bans named training-data scholars (Nussbaum, Modrak, Kisiel, Caston, Frede) and applies a work-level restriction (author-in-corpus ≠ all their works authorized).
2. **Citation enforcement as the load-bearing gate.** Because the Quality Gauntlet is known-degraded (§6), citation enforcement is intended as the primary quality signal — `CitationEnforcer` runs in auto-correct mode with a quotation-similarity floor of **0.70**. *Caveat:* `CitationEnforcer` fires only when a corpus-constraint allow-list has sources. In the `from-evidence` path this constraint is rebuilt fresh from verified spans, so enforcement runs; in a full `run()` the constraint is frequently **never built** (see Stage 2 and §6), so the enforcer may not fire on that path.
3. **Trust-tiered evidence with human-in-the-loop verification.** Every quote carries a derived gold/silver/bronze/red trust tier; only verified statuses may support asserted prose; humans can verify/reject/flag/OCR-correct. *Caveat:* the engine's *automatic* verification, as constructed, matches each quote against a text blob that already contains it (Stage 4 self-verification, §6), so the genuine evidentiary gate is the human review in the dashboard, not the auto-verifier.
4. **Edge coherence & tension awareness.** Cross-author contradictions are surfaced preventively (Stage 8a tension directive) and audited post-hoc (edge-coherence / tension-awareness gates; the stress test's adversarial contradiction retrieval), so the draft acknowledges rather than harmonizes conflict.
5. **Verbatim fidelity.** Quotation-fidelity targets of ~70–90% recur across the enforcement and validation layers.
6. **Closed learning loop.** Both system-caught issues and human corrections feed SoNA trajectory learning (`recordFeedbackLearning`, `corrected_text`, `trajectory_id`).

## 2. THE STEP-BY-STEP PIPELINE (the spine)

The authoritative ordering is `ICPOrchestrator.run()`. Each stage below gives **(a)** name/purpose, **(b)** implementing functions/modules, **(c)** inputs from prior stages, **(d)** outputs, **(e)** interactive gate / dashboard action, and **(f)** how it builds forward toward the final draft.

> **Stage-labeling conflict (Stages 5–6), unresolved.** The line-numbered `orchestrator-spine` and `persistence-run` briefs agree that **Stage 5 = claim generation** (`claimProvider` → Toulmin `ClaimMap`) and that the **`WritingContract` is built inside Stage 6** (`contractBuilder.build`, after atoms/binding). The `design-docs` brief instead labels Stage 5 "WritingContractBuilder" and Stage 6 "ClaimAtomBinder." This account follows the line-numbered source (claims at Stage 5; contract built within Stage 6) and flags the discrepancy.

### Stage 1 — Prompt → PromptSpec (Decomposition)
- **(a) Purpose.** Turn a raw prompt into a structured research brief: facets, research questions, retrieval terms, success criteria, and suggested sources.
- **(b) Implements.** `this.decomposer.decompose(userPrompt)` → `PromptDecomposer.decompose` (`prompt-decomposer.ts`). If an `LLMDecompositionProvider` is injected, `LLMDecompositionProviderImpl.decompose` calls `router.callJSON` at `costTier:'high'` (Anthropic), `temperature:0.3`, under `DECOMPOSITION_SYSTEM_PROMPT`; otherwise `fallbackDecompose()` (regex `extractKeyPointsFromTopic` + stopword-stripping `extractTerms`). Each `ProposedFacet` → validated `Facet` via `createFacet()` (assigns `facet_id=randomUUID()`, `evidence_policy_for_kind`, `atoms_mode`, `reverse_check_mode` — forced `'off'` for `exploratory` facets). `validateDecompositionResult`/`validateProposedFacet` hard-validate (≥1 facet or throw).
- **(c) Inputs.** The raw `userPrompt` string only.
- **(d) Outputs.** `promptSpec: PromptSpec` = `{original_prompt, research_questions, required_facets[], optional_facets[], retrieval_lexicon: Map<facet_id,string[]>, success_criteria: Map, suggestedPrimarySources?, suggestedSecondarySources?}`. Each facet's **description is designed to double as the semantic-search query** (50–100 words, self-contained), with 3–8 retrieval terms. An **evidence gate** runs during decomposition: `validateFacetEvidence(terms)` does a live probe `retrieval.retrieveContext(query, {maxChunks:3, minRelevance:0.5})`; facets with ≥`minRetrievalHits` (default 1) become `required_facets`, the rest are auto-demoted to `optional_facets`. The system prompt prepends a tiered corpus catalog (`buildCorpusCatalog()`) so suggested sources are grounded in real corpus works and non-corpus authors are forbidden.
- **(e) Interactive gate.** The **decompose refinement loop** is the primary interactive hook of intake: `DecompositionOptions.previousFacets + feedback` drive `buildRefinementPrompt` (`REFINEMENT_PREAMBLE`) for user-reviewed re-decomposition. `run()` itself does not pause — it is invoked once per (possibly already-refined) spec. In the dashboards, Stage 1 is triggered by `POST /session` (§4). Facets are later editable via `PUT /facets/:id/:facetId`.
- **(f) Builds forward.** Facets are the organizing key threaded through *every* later artifact via `facet_id`. The retrieval lexicon directly seeds Stage 2's queries.

### Stage 1b — Source-priority merge
- **(a) Purpose (as designed).** Elevate the decomposer's suggested works into the retrieval admission policy.
- **(b) Implements.** Inline in `run()` (lines 212–242).
- **(c) Inputs.** `promptSpec.suggestedPrimarySources/SecondarySources` + the caller's `sourcePriority: SourcePriorityConfig`.
- **(d) Outputs.** Mutates `sourcePriority.primarySources/.secondarySources` **in place**, deduping by `author::title`. No new object is emitted.
- **(e) Gate.** None.
- **(f) Builds forward — corrected.** *The synthesis claimed this "feeds Stage 2's source scope." Verification shows it does not.* `run()` calls `facetedRetrieval.retrieveForAllFacets(promptSpec, sourceScope)` (lines 250–253) with only two arguments; the merged `sourcePriority` object is **never read again anywhere in `run()`** — not by retrieval, claim generation, or any later stage. Its only observable effect is the in-place mutation of the caller's object. In the current `run()` codepath, Stage 1b is effectively a dead-end write; downstream retrieval admission is shaped by `sourceScope` alone.

### Stage 2 — Faceted Retrieval → QuoteSpans
- **(a) Purpose.** For every facet, pull candidate evidence from the corpus and materialize it as sentence-level quote spans.
- **(b) Implements.** `this.facetedRetrieval.retrieveForAllFacets(promptSpec, sourceScope)` (`faceted-retrieval.ts`). Iterates `required` then `optional` facets, pulling terms from `retrieval_lexicon.get(facet_id)` and calling `retrieveForFacet`. The query is built by `buildSemanticQuery` (prefers `facet.description` when >30 chars). With `sourceScope.corpus_config.collections`, it runs **per-collection parallel `retrieval.hybridSearch(query, terms, {semantic:0.7, keyword:0.3}, {maxChunks, minRelevance, collections:[c], diversityBoost:true})`**, flattens/dedups by `docId:page_start`, and sorts by `relevanceScore`; it falls back to a single `hybridSearch`, then to a bare `retrieveContext`. `extractSpansFromChunk` splits each matched chunk into sentences (≥20 chars) — every sentence becomes a candidate `QuoteSpan` with `verification_status:'flagged'`, identity fingerprints (`computeTextFingerprint`, `computeContextHash`, `computeSpanFingerprint`), and a `buildProvenanceScorecard` (`fidelity_score=relevanceScore`, `estimateOCRRisk`, `estimateAuthorityTier`). `applyCandidateAdmission` filters by the loose `candidate_rules` bar (Phase-1 admission); `computeCoverage` + `checkScarcity` emit `EvidenceScarcityWarning[]`.
- **(c) Inputs — corrected.** `promptSpec` and `sourceScope` only. (The synthesis also listed "merged sourcePriority"; per Stage 1b, that object is not passed to retrieval.)
- **(d) Outputs.** Pushes `result.spans` into `session.quote_spans`; `emitRetrievalEvent` per facet. Then the **WS3** block (lines 261–268): `this.retrievedChunks = getChunksFromSpans(session.quote_spans)`, and, *if any chunks exist*, `buildCorpusConstraint(retrievedChunks, {enforcement:'strict', minRelevance:0.5})` → `this.corpusConstraint` (the corpus allow-list later consumed by Stage 9 enforcement). Checkpoint `retrieval_complete`.
  - **Important correction.** `getChunksFromSpans` (line 1033) keeps only `auto_verified`/`human_verified`/`human_corrected` spans. At Stage 2, verification has not yet run (that is Stage 4), so **every span is still `flagged`**, `this.retrievedChunks` is empty, the `length > 0` guard is not satisfied, and **`buildCorpusConstraint` is skipped — `this.corpusConstraint` is typically NOT built at Stage 2 in the normal full run.** The only later opportunity to populate it in `run()` is the `auto_verified` bridge-enforced spans appended at Stage 6b — but whether WS3 re-runs after Stage 6b to rebuild the constraint is not established in the briefs (flagged in §6). The practical consequence: on the full-`run()` path, the Stage-9 `CitationEnforcer` branch (guarded on `corpusConstraint` having sources) may never fire. The `from-evidence` path avoids this by building its own constraint fresh from verified spans (§2.12).
- **(e) Interactive gate.** An optional evidence-augment loop in the dashboards: `POST /retrieve/:id` re-runs retrieval against the stored spec, dedupes by `span_fingerprint`, re-ranks the full set, and auto-verifies only the new spans.
- **(f) Builds forward.** Spans are the evidence root for everything after. The (intended) corpus-constraint object is the citation allow-list for Stage 9 — subject to the "not built at Stage 2" caveat above.

### Stage 3 — Canonicalization → Ranking
- **(a) Purpose.** De-duplicate near-identical spans and rank them so the best evidence is preferred.
- **(b) Implements.** `this.quoteRanker.canonicalizeAndRank(session.quote_spans, session.facets)` (`quote-ranker.ts`) → `{clusters, ranked, activeSet}` in five internal steps: `canonicalize` (3-pass: anchor-first `doc_id:source_anchor` grouping → `clusterByNgrams` 7-gram Jaccard ≥0.6 greedy clustering for spans ≥60 chars → hash fallback for short spans) → `assignCanonicalIds` (stamps `canonical_span_id`, `alias_span_ids`, `canonical_fingerprint`) → representatives (`sortByFidelity`) → `rank` → `buildActiveSet`. `rank` scores each span = `facetAlign·0.35 + roleWeight·0.25 + bindingPotential·0.20 + authority·0.10 − redundancy·0.05 − lengthPenalty·0.05` (per `DEFAULT_QUOTE_RANK_SPEC`); `bindingPotential=1.0` if the span's `quote_id` is already in a binding (else 0.3), so ranking can be re-run post-binding.
- **(c) Inputs.** `session.quote_spans` (candidate spans), `session.facets`.
- **(d) Outputs — corrected.** Overwrites `session.quote_spans = ranked` (line 280); sets `session.active_quote_set = activeSet` (line 281). *The synthesis claimed Stage 3 also "freezes the `canonical_registry_snapshot`." Verification shows it does not:* `canonicalizeAndRank` receives arrays, not the session, and returns only `{clusters, ranked, activeSet}`. Neither Stage 3 nor `createICPSession` (icp-types.ts:1608–1634) ever populates `session.canonical_registry_snapshot`; it stays **undefined** and is passed as `undefined` into `autoVerifier.verifyBatch` at Stage 4 (line 1178). The "deterministic Stage-B scoring against a frozen registry snapshot" is therefore aspirational — the auto-verifier operates on an undefined snapshot in the shipped path (see §3 and §6).
- **(e) Gate.** None directly; the Evidence panel sorts by confidence/source/page over the ranked set.
- **(f) Builds forward.** The ranked, canonicalized set is what verification runs on and what generation ultimately draws from. At this point spans are still **`flagged`** (unverified).

### Stage 4 — Tiered Verification (the intended evidentiary gate)
- **(a) Purpose.** Decide, per span, whether the quoted text is actually present in the source document, and set a status that governs downstream eligibility.
- **(b) Implements.** `await this.verifyQuotes(session)` (line 1155): groups spans by `doc_id`, fetches clean text via `deps.getCleanText(docId)`, calls `this.autoVerifier.verifyBatch(spans, cleanText, canonical_registry_snapshot)` (`auto-verifier.ts`), then `applyResults` writes each span's `verification_status` + `auto_confidence`. Inside `AutoVerifier.verify`: `maybeRepairOCR()` (repair-then-verify, vLLM-only, `forceBackend:'vllm'`, guarded by `repairDivergesTooMuch()` >15% char change) → **Stage A** `runStageA()` deterministic match (`match_type: exact|normalized|approximate|none`; anchors never fail Stage A) → **Stage B** `computeStageBSignals()` (exactness, `ocr_risk_score`, `quote_length_factor`, `doc_authority_tier`, `canonical_overlap`, `anchor_confidence`, weighted by `DEFAULT_STAGE_B_WEIGHTS`) → `computeAutoConfidence()` weighted sum → `determineStatus()`. `emitVerificationEvent` per quote.
- **(c) Inputs.** Ranked `session.quote_spans`, the (undefined) `canonical_registry_snapshot`, clean document text.
- **(d) Outputs.** Each span's `verification_status` ∈ 7 states; the downstream-eligible set is `VERIFIED_STATUSES = {auto_verified, human_verified, human_corrected}` (note: `stale_verified` does **not** pass). Status rule: Stage-A fail → `flagged` (or `auto_rejected` below `flaggedThreshold` 0.50); Stage-A pass + confidence ≥ `autoVerifyThreshold` → `auto_verified`; ≥0.50 → `flagged`; else `auto_rejected`. **Operative threshold: 0.65** — the class default `DEFAULT_CONFIG.autoVerifyThreshold` is 0.85, but `icp-provider-factory.ts:103` overrides it to **0.65** because "corpus relevance scores typically range 0.76–0.83, which would all be 'flagged' at 0.85." Checkpoint `verification_complete`.
- **(d′) Critical shipped-build correction — self-verification.** `deps.getCleanText` is **optional and is never supplied** by `ICPProviderFactory` or the routes. When it is absent, `verifyQuotes` falls back to `cleanText = spans.map(s => s.text).join(' ')` (icp-orchestrator.ts:1171–1173) — i.e., each span is matched against a concatenation that **already contains it**, so `runStageA()` finds a match trivially and Stage A passes for essentially all spans. As constructed, the automatic verifier therefore **verifies quotes against themselves**; it filters almost nothing. This does not disable the *human* gate (below), but it means the automatic tier is not the evidentiary filter it is described as. (Compounding this, the `canonical_registry_snapshot` passed to `verifyBatch` is `undefined`, per Stage 3.)
- **(e) Interactive gate — THE first (and, in practice, the only real) human evidentiary gate.** `run()` never blocks: with default `autoVerifyOnly:true` (line 115) it runs straight through. Human review happens in the dashboards via `POST /verify {sessionId, quoteId, status, correctedText?}` (approve/reject/flag; `human_corrected` overwrites the span text) and OCR correction via `POST /patch`. Because the auto-verifier self-verifies, this human adjudication is where evidence is genuinely accepted or rejected.
- **(f) Builds forward.** Only verified spans may enter binding (Stage 6's `applyEligibleAdmission`) and only verified spans are eligible for `from-evidence` generation. This is the *intended* load-bearing evidentiary filter — load-bearing only to the extent the human exercises it, given the self-verification caveat.

### Stage 5 — Claims (Toulmin claim generation)
- **(a) Purpose.** Produce the argument's backbone: a small set of Toulmin claims grounded in verified evidence.
- **(b) Implements.** If `deps.claimProvider` is present, `claimProvider(promptSpec, session.quote_spans)` → `LLMClaimProvider.generateClaims` (`llm-claim-provider.ts`). `buildClaimPrompt` groups spans into PRIMARY/SECONDARY/OTHER tiers, enforces a strictly closed-book corpus constraint, targets **4–6 Toulmin claims**, ≥60% grounded from primary; `router.call({costTier:'high', temperature:0.3, jsonMode:true})`. `parseAndRepairClaimsJSON()` does staged JSON repair; `validateSingleClaim()` requires a non-empty `claim`, ≥1 `grounds`, and a `warrant` (throws otherwise) and computes `ClaimQuality` (`toulminCompleteness 0.30 / warrantQuality 0.25 / evidenceStrength 0.25 / counterArgumentHandling 0.20`).
- **(c) Inputs.** `promptSpec` + verified `session.quote_spans`.
- **(d) Outputs.** `claims: ToulminClaim[]` + `session.claim_map: ClaimMap`.
- **(e) Gate.** None (no dedicated claim-review route in the analyzed files).
- **(f) Builds forward.** Claims are decomposed into atoms and bound in Stage 6; consumed by Stages 6–8.

### Stage 6 — Atom Decomposition → Binding (+ Writing Contract)
- **(a) Purpose.** Break claims into atomic propositions, bind each to verified evidence, demote the unbindable, and build the writing contract.
- **(b) Implements.** Per non-archived facet: `this.atomBinder.decompose(facetClaims, facet.facet_id)` (`claim-atom-binder.ts`) → `atoms` (main claim → `asserted`/`corpus_claim`; each `ground` → atom via `inferModality`/`inferKind`; `warrant` → `inferential`/`interpretive_move`; `qualification` → `hedged`; each gets `evidence_mode = defaultEvidenceMode(kind)`). Then `this.atomBinder.bind(atoms, session.quote_spans, session.facets)` → `{bindings, unbound_atoms, block_reasons}`: `applyEligibleAdmission` (Phase-2 — only `VERIFIED_STATUSES` + required authority tier), `findCandidateQuotes()` scores term overlap (threshold **≥0.2**, top-3); **a claim is "bound" when ≥1 eligible verified quote matches**, producing a `ClaimBinding{binding_id, claim_id, atom_ids, quote_ids, support_kind, staleness_status:'current'}` and setting `atom.bound_quote_ids`. Zero candidates under `strict` strictness → `unbound_atom` + `BlockReason{action:'bind', rule_id:'strict_evidence_required'}`. `this.atomBinder.demoteToHypothesis(...)` → `session.hypothesis_claims` (unbound atoms preserved, grouped by parent claim, timestamped `demotion_reason`). Finally `this.contractBuilder.build(...)` → `session.writing_contract`. Cross-author bindings get `cross_author_tension` flags.
- **(c) Inputs.** `claims`/`claim_map` (Stage 5), verified `session.quote_spans` (Stage 4), `session.facets`.
- **(d) Outputs.** `session.atoms`, `session.bindings`, `session.hypothesis_claims`, `session.writing_contract`, accumulated block reasons.
- **(e) Interactive gate.** Manual binding in the dashboards: `POST /bind/:id {atomIds, quoteIds, supportKind, warrantNote?}` and `DELETE /bind/:id/:bindingId`. **Caveat:** `session.atoms` is populated only by the full orchestrator run, so `/bind` is inert in a pure `from-evidence`/manual flow (§6). Atom-split migrations "require interactive resolution (UI wizard)" — the one explicit human-gate marker in `claim-atom-binder.ts`.
- **(f) Builds forward.** Atoms + bindings feed the stress test (7) and paragraph plan (8); hypotheses are excluded from asserted prose; cross-author tension flags feed Stage 8a.

### Stage 6b — Cross-Author Bridge Enforcement
- **(a) Purpose.** Guarantee that a claimed cross-author "bridge" actually has both authors' evidence present.
- **(b) Implements.** Inline (lines 349–435); dynamic-imports `getActiveBridges`/`extractTopicWords`. If a facet activates a bridge requiring ≥2 authors and a required author is absent from current spans, it forces `deps.retrieval.retrieveContext(..., {whereFilter:{author_raw:{$eq:author}}})` and appends synthesized `QuoteSpan`s (`verification_status:'auto_verified'`, `source_anchor:"… (bridge-enforced)"`). Best-effort (all failures swallowed).
- **(c) Inputs.** `session.facets`, `session.quote_spans`, active bridge definitions.
- **(d) Outputs.** Additional bridge-enforced spans appended to `session.quote_spans`. Because these carry `auto_verified` status, they are the one route by which `getChunksFromSpans` could return non-empty chunks — i.e., the only path by which `this.corpusConstraint` might become non-empty in a full `run()` (subject to the rebuild-timing caveat in Stage 2 / §6).
- **(e) Gate.** None (automatic, non-fatal).
- **(f) Builds forward.** Ensures the generator has both sides of a bridge so tension directives (8a) and edge-coherence gates (10) have material to work with.

### Stage 7 — Stress Test
- **(a) Purpose.** Probe each atom's evidential robustness and flag contested/weak claims before drafting.
- **(b) Implements.** `this.stressTester.stressTest(session.atoms, session.bindings, session.quote_spans, claims)` (`claim-stress-tester.ts`) → `session.stress_test_report`. Per-atom `testAtom`: `checkWarrantAdequacy` → `adequate|weak|missing` (INFERENCE atoms need a parent warrant with `warrantGenerality ≥ 0.6`; DIRECT_QUOTE/PARAPHRASE need a `current` binding); `checkContestedScholarship` (≥2 cross-doc spans + contradiction markers); `runContradictionRetrieval` (adversarial "Red Teamer" negation query, `minRelevance 0.7`). - **(d) Outputs.** `session.stress_test_report` (`AtomStressResult[]` + `EvidenceScarcityWarning[]`).
- **(e) Interactive gate.** The legacy panel offers `POST /stress-test/:id` — but **this route is a read-only stub**: it returns `session.stress_test_report` if present, else a "use the full pipeline" message. Real stress-testing happens only inside `run()`.

### Stage 8 — Paragraph Plan → Validate → Generate
- **(a) Purpose.** Lay out paragraphs over atoms, validate coverage, then generate constrained prose.
- **(b) Implements.**

  - **Style (WS1).** Resolve `stylePrompt` from `deps.stylePromptProvider(styleProfileId)` else `this.stylePromptCache` → `session.style_prompt`. Checkpoint `binding_complete`.
  - **Generate.** Guarded by `validation.valid || atomsMode!=='strict'`: `this.generator.generate(plan, atoms, bindings, quote_spans, facets, atomsMode, reverseCheckMode, deps.generationProvider, stylePrompt)` → `generationResult`. Per plan entry, in order: `buildParagraphPrompt` (STYLE / CONSTRAINTS / MANDATORY CITATION FORMAT `(Author, *Title*, p. X)` / STRICT CLOSED-BOOK CORPUS CONSTRAINT / WORK-LEVEL RESTRICTION / CITATION DENSITY ≥1 cite per 2–3 sentences / inline `[supports: atom_id]` tags only in `strict` / ATOMS TO COVER / APPROVED QUOTES verbatim / discourse context) → `provider.generateParagraph()` (temp 0.7, 2000 tok, `costTier:'high'`) → `ProseSanitizer.sanitize()` → the **inline-validation retry loop** (`ICPInlineValidator.validateParagraph`, up to `maxInlineRetries=2`) → `parseParagraphOutput()` (`strict`→`parseInlineConstraintTokens`; `analytics`→`generateSentenceMapping`; `off`→plain split) → `runDriftDetection()` → `updateDiscourseState`. Checkpoint `generation_complete`.

So in the shipped construction there is no per-paragraph generate→validate→feedback→regenerate loop; `runDriftDetection` still runs and emits flags/BlockReasons, but nothing regenerates a paragraph on a failed inline check. Treat the inline loop as latent, not active (see §2.13 and §6).
- **(c) Inputs.** `session.atoms`, `session.bindings`, `session.quote_spans`, `session.facets`, `session.style_prompt`.
- **(d) Outputs.** `session.paragraph_plan`, `session.generated_text` (`Map<paragraph_id,string>`), `session.sentence_scopes`, `session.paragraph_ledger`, generation block reasons.
- **(e) Interactive gate.** In the dashboards this is the culminating "Generate" button (`POST /adapter/generate/:id`). Live-streaming section-complete/budget-warning/generation-complete events and a Cancel/abort control exist in the legacy panel via WebSocket (partial — §6). The read-only `POST /generate/:id` route is a stub that only returns existing text.
- **(f) Builds forward.** Generated text is what enforcement, gauntlet, and manifest all consume.

#### Stage 8a — Preventive edge coherence (nested in Stage 8)
- **(a) Purpose.** Force the LLM to acknowledge cross-author contrasts rather than smoothing them over.
- **(b) Implements.** For each plan entry, maps bound atoms → topic words → `getActiveTensions`; if cross-author tensions are found, builds a `tensionDirective` ("CROSS-AUTHOR TENSIONS … you MUST acknowledge each contrast — do not harmonize") and appends it to `stylePrompt`. Records `session.quality_gates.preventive_edge_check` (icp-orchestrator.ts:554).
- **(c) Inputs.** Bound atoms per paragraph, active tension registry, `stylePrompt`.
- **(d) Outputs.** Augmented `stylePrompt` (consumed by the very next `generate` call); the `preventive_edge_check` field on `session.quality_gates`.
- **(e) Gate.** None (automatic).
- **(f) Builds forward.** Directly conditions generation so the output survives the post-hoc tension-awareness gate at Stage 10.

**Inline drift detection (inside Stage 8 generation).** `runDriftDetection` runs a **forward** check (declared atoms exist) and a **reverse** check via `PropositionExtractor.extractPropositions` (`proposition-extractor.ts`): undeclared claim-bearing predicates are graded definitional/causal/universal → `BLOCK`, attribution/hedged-causal → `WARN`, rhetorical glue → `OK`. In `strict` atomsMode a `BLOCK` emits a `BlockReason{rule_id:'drift_block'}`. (The `ICPInlineValidator.validateParagraph` inner loop — required quotes present via char-trigram similarity ≥0.70; citation surnames ∈ corpus `allowedLastNames`; atom keyword coverage ≥0.3 — is the design's self-correcting retry, but it is **not wired** in the shipped build, so its failures do not trigger regeneration; see the Stage-8 correction above.)

### Stage 9 — Citation Enforcement + Scrubbing
- **(a) Purpose.** Assemble the draft and mechanically enforce/repair citations and strip non-corpus contamination.
- **(b) Implements.** `assembledProse = this.assembleFinalProse(session)` (line 1235; orders paragraphs by `paragraph_order`, joins with `\n\n`, drops empties). **9a:** regex-inserts `[CITATION NEEDED]` on multi-sentence paragraphs lacking a `(…\d…)` citation; initializes `session.review_results` (claim coverage from `sentence_scopes`). - **(c) Inputs.** `session.generated_text`, `session.paragraph_plan`, `this.corpusConstraint`, `this.retrievedChunks`.

### 2.12 The `from-evidence` fast path (what the shipped V2 UI actually drives)
When invoked via `POST /adapter/generate/:id {mode:'from-evidence'}`, the engine runs `generateFromEvidence(session, factory.router, new SmartRetrievalLayer())` — a **leaner pipeline that reuses the same enforcement building blocks** rather than the full 11 stages:

1. Filter `quote_spans` to `{auto_verified, human_verified, human_corrected}` → `ContextChunk[]` (**throws if zero verified**, enforcing the Stage-4 human gate);
2. `buildCorpusConstraint(chunks, {enforcement:'strict'})` — *this is where the citation allow-list actually gets built on the shipped path*;
3. subsections = non-archived facet names;
4. style prompt;
5. `buildGoldStandardPrompt(...)` — **with `knowledgeUnits: []` and `structuralEdges: []`** (see correction below);
6. a **single one-shot** `router.call({userPrompt, maxTokens: GOLD_STANDARD_CONFIG.opusMaxTokens, costTier:'high'})`;

then a fixed quality-gate cascade mutating `text`: (7) `CitationEnforcer.enforce` (auto-correct, 0.70), (8) `scrubNonCorpusAuthors`, (9) `stripBareApaParentheticals`, (10) `stripEndnoteLeaks`, (11) `ProseSanitizer.sanitize` ×2, (12) `createDefaultGauntlet().runGauntlet`, (12b) `validateEdgeCoherence`, (13) `EndnoteGenerator.generateEndnotes`. Returns `{generatedText, qualityGates, success}`; the route stores `generated_text = Map([['full', text]])` and sets `pipeline_phase='GENERATED'`.

**This path does not populate atoms/bindings/plan/stress-test/manifest** — it collapses Stages 5–8 into a single gold-standard prompt call and reuses the Stage 9–10 cascade.

**Correction (resolves the synthesis's "not determined").** `generateFromEvidence` (icp-api-routes.ts:1561–1577) is a **single one-shot call** — there is no multi-step, `investigateV1`, or rolling-context work inside it. And because step 5 passes `knowledgeUnits: []` / `structuralEdges: []`, **reasoning-edges and knowledge-units are NOT injected into the shipped from-evidence generation prompt.** They are loaded (from `god-reason/reasoning.jsonl` and `god-learn/knowledge.jsonl`, topic-filtered and corroboration-sorted) **only by the separate `POST /build-gold-prompt` preview route** (icp-api-routes.ts:1233–1273), which builds a prompt for on-screen inspection and never feeds actual generation. So the gold-standard prompt shown in the preview is *not* the prompt used to generate.

### 2.13 The revise/retry loops (where they actually live)
There is **no in-orchestrator revise/retry loop and no cycle limit** — `run()` executes each stage once. Revision cycles exist only:

- **Inside `CitationEnforcer`** (auto-correct) — the one genuinely live self-correcting loop *inside* the engine, and only when the corpus constraint has sources (reliable on the `from-evidence` path). The generator's **drift/reverse-check** (`reverseCheckMode`, default `'warn'`) runs but only *flags* (BlockReasons/WARNs); it does not regenerate. The design's **inline-validation retry loop** (`maxInlineRetries=2`, "generate → validate → feedback → regenerate") is **inert** in the shipped build — `deps.inlineValidator` is never wired (Stage-8 correction). *This revises the synthesis, which listed the inline loop as one of two live internal loops; in the shipped construction it is latent.*
- **Externally, driven by the dashboard:** `POST /adapter/regenerate/:id` re-invokes `orchestrator.run` and sets `pipeline_phase='REGENERATED'`; "Modify & Regenerate" returns the user to the Evidence gate. The legacy panel's **Investigation → "Re-generate with Prevention Plan"** loop (`INVESTIGATED → REGENERATED`) is documented but orphaned under the shipped `orchestrator.run()` path (§6).
- A `session.revision` counter exists and is recorded in checkpoints, but it is incremented by `emitSessionEvent`, **not** by `run()`'s stage progression.

## 3. THE DATA MODEL / PROVENANCE CHAIN

Types live in `icp-types.ts` (types + defaults + four helpers; the step functions live elsewhere). The single mutable state bag is **`ICPSession`** (L1000–1094), created by `createICPSession(sessionId, promptSpec, sourceScope)` (L1608) with `pipeline_phase:'CREATED'`. Every step reads/writes `session.*`; `emitSessionEvent` (L1637) increments `session.revision` and appends to the append-only `event_log` (an audit trail — explicitly *not* full event sourcing; state is authoritative).

**Canonical phase machine** (`ICPSession.pipeline_phase`, L1064):
`CREATED → DECOMPOSED → RETRIEVED → VERIFIED → BOUND → GENERATED → PARTIALLY_GENERATED → INVESTIGATED → REGENERATED → VALIDATED → EXPORTED`.

**Atomic logged operations** (`ICPEventAction`, L115–138): `retrieve, verify, patch, bind, prune, stress_test, plan_validate, generate, drift_flag, review_fail, export, atom_migrate, atom_auto_migrate, polish_normalize, justified_relaxation, facet_migrate, investigate, regenerate, validate_gate, abort, feedback, budget_warning, section_complete`.

**The provenance chain — each artifact references the ones before it:**

1. **`PromptSpec`** (L554) ← raw prompt. Carries `research_questions`, `required_facets`/`optional_facets: Facet[]`, `retrieval_lexicon: Map<facet_id,string[]>`, `success_criteria`, `suggested*Sources`. **`Facet`** (L512) is the organizing key: `facet_id`, per-facet `EvidenceStrictness`, `evidence_policy_for_kind: Map<AtomKind,EvidenceRequirement>`, `atoms_mode`, `reverse_check_mode`. Threaded through *every* later artifact via `facet_id`.
2. **`QuoteSpan`** (L309) ← retrieval over `SourceScopeSpec` (L482). The evidence root, with **three-tier identity** (`quote_id` UUID / `span_fingerprint` pre-canonical / `canonical_fingerprint`) and references to `doc_id`, `clean_text_range`, `clean_range_hash`, `patch_epoch`, `normalization_policy_version`, context hashes, and `provenance_scorecard: ProvenanceScorecard` (fidelity, ocr_risk, cluster_size, prior_usage_count, doc_authority_tier). **Invariant: offsets are never identity.** OCR corrections are separate **`OCRPatch`** (L446) objects (document-/range-first, not quote-first); `patch_epoch` + `clean_range_hash` detect staleness later.
3. **Verification artifacts** ← QuoteSpan + clean text. `StageAResult` (L1360) → `StageBSignals` (L1370, weighted by `DEFAULT_STAGE_B_WEIGHTS` L1395: exactness .25, ocr_risk .20, length .15, authority .10, canonical_overlap .20, anchor .10) → `AutoVerificationResult` (L1407) with `auto_confidence` + `recommended_status`. Mutates `QuoteSpan.verification_status` (`VerificationStatus`, 7 states, L17). `computeTrustTier()` (L390) *derives* gold/silver/bronze/red on read from status + scorecard via `DEFAULT_TRUST_TIER_POLICY` (L1564: gold **0.85**, silver **0.65**, bronze **0.45**). `VERIFIED_STATUSES` (L1547) = {auto_verified, human_verified, human_corrected} — the gate binding requires. `SourceAdmissionPolicy` (L228) is two-phase: *candidate* (minimal bar to reach the verification UI) vs *eligible* (full bar before binding).
4. **Claim layer** ← verified spans + Toulmin `ClaimMap` (imported L10). `ClaimAtom` (L617): `parent_claim_id`→ClaimMap, `bound_quote_ids[]`→QuoteSpan, `facet_id`→Facet, `evidence_mode` (`defaultEvidenceMode(kind)` L1513). `ClaimBinding` (L726): `claim_id` + `atom_ids[]` + `quote_ids[]` + `support_kind` + `staleness_status`. Weak atoms → `HypothesisClaim` (L746, retains `source_bindings`). Budget: `QuoteBudgetPlan` (L774) + `ActiveQuoteSet` (L788) prune via `DEFAULT_QUOTE_RANK_SPEC` (L1554: facet_alignment .35, role .25, binding_potential .20, authority .10, redundancy .05, length .05).
5. **`StressTestReport`** (L808) / `AtomStressResult` (L821, `warrant_verdict`, `contested`, `remediations: StressRemediation[]` L833) / `EvidenceScarcityWarning` (L848) ← atoms.
6. **Plan/generation** ← atoms/bindings. `WritingContract` (L576: thesis, scope, `required_quotations: QuoteSpan[]`, `section_outline`, `facet_requirements`) + `ParagraphPlanEntry[]` (L692: `atom_ids[]`, `required_quotes[]`, `section_id`). `DiscourseState` (L708) threads coherence. Prose → **`generated_text: Map<string,string>`** (L1022) — **keyed by `paragraph_id`** (set at L585, read at L1238), *not* by `section_id`; `SentenceScope[]` (L674: `supports_atoms[]`→atoms, optional `adds_atoms: NewAtomDeclaration[]`). **`ParagraphLedger`** (L923) is **deterministically recomputed** (not stored state) from plan+scopes+bindings+strictness+drift+resolutions; carries `DriftFlag[]` and `WarnResolution[]` (L900). *(Correction: the synthesis labeled `generated_text` `Map<section_id,string>`; the declared type is `Map<string,string>` keyed by paragraph_id.)*
7. **Review/QA** ← generated text. `ReviewResults` (L1217: `quote_fidelity`, `claim_coverage` orphan sentences, `facet_coverage`, `multi_claim_sentences`, `passed`, `failures`) + `QualityGateResults` (L1099) aggregating the WS gates: `citation_enforcement, gauntlet, endnotes, bibliography, sanitization, style_profile, author_scrubbing, apa_stripping, edge_coherence, tension_awareness, unanchored_edges, ocr_quality`, **plus `author_conflict_events`** (H-12, populated by `deriveAuthorConflictEvents`, icp-orchestrator.ts:895) **and `preventive_edge_check`** (Stage 8a, set at icp-orchestrator.ts:554). **Numeric pass thresholds for these gates are NOT encoded in `icp-types.ts`** — only structural shapes + booleans; the only hard numbers are trust-tier (0.85/0.65/0.45), Stage-B weights, rank weights, and `token_similarity_threshold: 0.99` (`DEFAULT_SEMANTIC_DELTA_POLICY` L1581).
8. **Export** ← everything. `ExportPackage` (L1334): `final_prose` (Markdown), `endnotes`, `bibliography`, `claim_map_appendix` (Mermaid), `evidence_ledger`, `paragraph_ledger`, `run_manifest`, `methodology_trace` (advisor-facing, derived from the user-visible event log). Reproducibility snapshot `RunManifest` (L1274): `corpus_hash`, `patch_epoch`, claim_map/bindings/hypothesis/ledger/migration snapshots + `PolicyArchive`, plus `pre_polish_draft` and `corpus_version_diff: CorpusVersionDiff` (L1316).

**Staleness / change-propagation (latent).** `OCRPatch` commits bump `patch_epoch`; `QuoteSpan.clean_range_hash`/`patch_epoch` + `DocStalenessIndex` (L1455), `StalenessVerdict` (L1422), and `LocateResult` (L1441) mark spans/bindings `stale`, cascading to `ClaimBinding.staleness_status` and `HypothesisClaim`. `StalenessEngine` (`quote-span-staleness.ts`) is the sole authority for span math (`markCandidatesOnPatchCommit`, `computeStaleness`, `locateSpan` via `rebaseRange`→`searchInWindow`→`disambiguate`). It also includes a **staleness circuit breaker** (`quote-span-staleness.ts:306`; `config.circuitBreakerThreshold` / `DEFAULT_CIRCUIT_BREAKER_THRESHOLD`): inside `markCandidatesOnPatchCommit`, when the count of patch-intersecting candidate spans in a document exceeds the threshold, the engine escalates to marking **all** spans in that document as staleness candidates — a conservative blast-radius fail-safe. **This entire machinery is currently latent** — in `run()` `corpusHash='initial'`, the patch store is not wired into the live pipeline, and `checkAnchorRegression` is a conservative stub returning `'ok'`.

**Correction — the canonical registry snapshot is not populated.** `CanonicalRegistrySnapshot` (L958) is described in the design as frozen at session start so Stage-B scoring is deterministic and never reads the live store. In the shipped `run()` codepath, **`session.canonical_registry_snapshot` is never populated** (neither Stage 3 nor `createICPSession` writes it), so it is `undefined` when passed into Stage 4's `verifyBatch`. The "deterministic scoring against a frozen registry" is aspirational; Stage B tolerates an undefined snapshot.

**Human-gate carriers in the data model.** `VerificationStatus` includes `human_verified`/`human_corrected`; `ICPEventActor` (L141) distinguishes `system`/`user`/`llm`; `JustifiedRelaxation` (L873, user rationale to lower facet strictness); `WarnResolution` (L900, human resolves reverse-check WARNs: rhetorical_glue/missing_atom/needs_hedge/scope_leak/attribution_missing); `BlockReason` (L861, required vs observed state + `minimal_remediations` = the interactive un-block prompt); `corrected_text: Map` (human-edit delta fed to SoNA via `trajectory_id`).

## 4. THE INTERACTIVE LAYER

### 4.1 The engine↔dashboard contract (`icp-api-routes.ts`)
All routes are created by `createICPRouter(options?)` and mounted at `/api/icp`. State is a module-level in-memory `Map<string, ICPSession>`; `getSession` 404s on miss; `serializeSession` is the canonical wire shape. `ICPRouterOptions.server` can supply a WebSocket emitter/abort controller, but **no route body in this file consumes it** (flag). Key routes:

| Route | Purpose |
|---|---|
| `POST /session` | Create session + run **stages 1–4** (decompose → retrieve → rank → verify) synchronously; returns `{sessionId, session, pipeline_stages}` |
| `GET /session/:id`, `GET /sessions`, `DELETE /session/:id` | Inspect / list / delete |
| `GET /facets/:id`, `PUT /facets/:id/:facetId` | Facet coverage view; mutate name/description/role/`strictness_override`/`allow_adds_atoms` |
| `POST /retrieve/:id` | Re-run retrieval, dedupe, re-rank, auto-verify only new spans |
| `POST /verify` | **Human verification gate** — set `verification_status`, overwrite text on `human_corrected` |
| `POST /patch` | OCR patch gate — build `OCRPatch` (author `'user'`), record via `emitPatchEvent` |
| `POST /bind/:id`, `DELETE /bind/:id/:bindingId` | Manual claim binding (inert without a full run) |
| `POST /build-gold-prompt/:id` | Prompt **preview** only (no LLM). Loads reasoning-edges + knowledge-units (topic-filtered, corroboration-sorted). **Its output is not the generation prompt** — the shipped `from-evidence` generation passes empty edge/KU arrays (§2.12) |
| `POST /adapter/generate/:id {mode}` | **Generate** — `full`→`orchestrator.run()`; `from-evidence`→`generateFromEvidence()` (single one-shot) |
| `POST /adapter/regenerate/:id` | Re-run → `pipeline_phase='REGENERATED'` |
| `POST /adapter/validate/:id` | Read-only: return computed gates + text |

### 4.2 Dashboard V2 — the 4-panel workflow (`icp-panel-v2.js`)
Module-level state `v2 = {sessionId, session, depth, panel, phase, subProgress, creating, selectedQuotes:Set}`; `depth`/`panel` persist to `localStorage`. 'auto_verified' : 'rejected'`, POSTing `/verify` per span; filters survivors; **throws "Insufficient evidence… Switch to Standard mode" if zero survive**; else `v2GenerateFromEvidence()` → `v2SwitchPanel('export')`. (Note: 0.85 is hard-coded here and differs from the engine's operative 0.65; Express sets `'rejected'`, not `'auto_rejected'`.)
  - **Standard/Full** → `v2SwitchPanel('evidence')`.
- Secondary (shown for `depth !== 'express'`, `v2RunToEvidenceOnly`, rendered at line 342 / defined at line 456) → **"Run to Evidence Only"**: temporarily forces Standard depth, calls `v2RunPipeline` (`POST /session`), and lands on the Evidence panel — a wired way to run intake and stop for review regardless of the selected depth.

## 6. GAPS / UNCERTAINTIES / KNOWN LIMITATIONS

**Interactivity vs. the engine.** Despite the name, `ICPOrchestrator.run()` executes **autonomously end-to-end** with no synchronous human pause. The interactive character is realized entirely at the dashboard/route boundary (verify, patch, bind, regenerate, feedback, export). Inside the engine, the only genuinely live self-correcting loop in the shipped build is `CitationEnforcer`'s auto-correct pass (and only when a corpus constraint exists). `autoVerifyOnly:true` (default) is the sole in-engine human toggle, and it defaults to *skipping* the human gate.

**Stage 4 auto-verification self-verifies (shipped build).** `deps.getCleanText` is optional and is never supplied by `ICPProviderFactory` or the routes, so `verifyQuotes` falls back to `cleanText = spans.map(s => s.text).join(' ')`. Each span is then matched against a concatenation that already contains it, so `runStageA()` passes trivially for essentially every span. The automatic verifier therefore filters almost nothing; the real evidentiary gate is the human verify/reject/flag in the dashboard. (Related: `session.canonical_registry_snapshot` is never populated in `run()`, so Stage B scores against an `undefined` snapshot.)

**The inline-validation retry loop is inert.** `ICPInlineValidator.validateParagraph` is gated by `if (this.inlineValidator)`; `deps.inlineValidator` is optional and is never wired by `ICPProviderFactory.create` or `getFactoryResult()`, and `new ICPInlineValidator` appears nowhere in `src`. The design's tightest revise loop (generate → validate → feedback → regenerate) does not run in the shipped construction. Forward/reverse drift detection still runs but only *flags*.

**The corpus constraint is typically not built on the full `run()` path.** WS3 (Stage 2) builds `this.corpusConstraint` only if `getChunksFromSpans` returns verified spans — but at Stage 2 no span is verified yet, so it is skipped. The only later population is `auto_verified` bridge-enforced spans at Stage 6b, and whether WS3 re-runs after 6b to rebuild the constraint is not established in the briefs. Consequence: the Stage-9 `CitationEnforcer` branch (guarded on the constraint having sources) may never fire on a full `run()`. The shipped `from-evidence` path avoids this by rebuilding the constraint fresh from verified spans.

**Stage 1b is a dead-end write.** The merged `sourcePriority` is mutated in place but never read again in `run()`; retrieval receives only `(promptSpec, sourceScope)`. Its intended effect on downstream retrieval admission is not realized in the current codepath.

**No engine-level revise/retry loop; `revision` not incremented by stages.** `run()` runs each stage once; there is no cycle limit. The gauntlet emits `revisionRequired`/`revisionGuidance` and `BlockReason`s but no loop consumes them inside the orchestrator. `session.revision` is bumped by `emitSessionEvent`, not by stage progression. Any true revision cycle is dashboard-driven (`/adapter/regenerate`, "Modify & Regenerate").

**Checkpoints ≠ resumable state.** `checkpoint()` writes only progress counters + a stage label to `{runsDir}/{session_id}.checkpoint.json` at 5 points; `static resume()` returns a resume-*point* indicator, not restorable `ICPSession` state. Full-state reproducibility is the terminal `RunManifest` (snapshot/save/load), not the checkpoints.

**`pipeline_phase` state machine is exercised by the route layer, not the orchestrator.** The `persistence-run` brief did not observe `run()` assigning `pipeline_phase` (stage tracking is via checkpoint strings), while the routes set `GENERATED`/`REGENERATED` via `(session as any)`. The phase enum is a mild inconsistency between the two layers.

**`session.atoms` (and therefore `/bind`) is inert in the `from-evidence`/manual flow.** Only the full `orchestrator.run()` path populates `atoms`; the from-evidence helper does not. Manual binding, atom-coverage in `/facets`, the Binding Builder, Stress Console, and Planner all show data **only after a `mode:'full'` run** — but the shipped V2 UI never calls `mode:'full'`.

**The shipped V2 flow never exercises the 11-stage scaffolding.** Because both Express and Standard/Full call `from-evidence`, the atoms/bindings/stress/plan/ledger/manifest machinery is not run by the shipped UI at all unless a caller hits `mode:'full'` directly. `v2GenerateFull()` exists but is wired to no control.

**`generateFromEvidence` is a single one-shot call, and reasoning-edges/KUs do not reach generation.** It does no multi-step/rolling-context work and passes `knowledgeUnits: []` / `structuralEdges: []`. The reasoning-edge and knowledge-unit loading (from `god-reason/reasoning.jsonl` and `god-learn/knowledge.jsonl`) happens only in the `/build-gold-prompt` **preview** route, which never feeds the actual generation prompt. Any account that implies the preview prompt equals the generation prompt is wrong.

**Threshold inconsistencies.** Auto-verify: class default 0.85 vs. factory-overridden operative **0.65** vs. Express-mode dashboard hard-coded **0.85** (and Express sets `'rejected'` rather than `'auto_rejected'` for sub-threshold spans). The "70% quotation fidelity" and "0.65 auto-verify" figures cited in project memory are **not literals in `icp-types.ts`** (only trust-tier 0.85/0.65/0.45, Stage-B weights, rank weights, and `token_similarity_threshold 0.99` are).

**Quality Gauntlet stage count and degradation.** Briefs disagree on the count: `design-docs` says **9 weighted stages @ 0.80 threshold**; project memory and the `dashboard-full` brief say **7 stages**; `dashboard-v2` renders whatever `stage_results` contains. More importantly, the user guide reports the gauntlet is **known-degraded — all stages return the 0.5 default** — which is the stated reason citation enforcement is supposed to be the primary signal. This conflict (7 vs 9 stages) is **unresolved**; numeric gauntlet pass thresholds are not encoded in `icp-types.ts`.

**`ICPPipelineAdapter` and the convergence machinery are unconfirmed / likely absent.** `design-docs` reports that `core/composition/icp-pipeline-adapter.ts` (documented "COMPLETE, 1,519 lines") **does not exist in the live tree** (only a stray reference in `retrieval-utils.ts`), and that the from-evidence path is served by the smaller `generateFromEvidence()` helper — which verification confirms is a single one-shot call. Consequently the documented **multi-step v1→`investigateV1`→v2 loop, `buildRollingContextSectionPrompt` rolling-context loop, COLD/WARM/HOT tiered compression, 12K-token auto-downgrade cascade, and `PipelineAbortController`** are **not present in the shipped generation path** — treat as aspirational / relocated.

**Investigation panel is orphaned.** It populates only under the old multi-step adapter path; the shipped `orchestrator.run()` does stress-testing, not `investigateV1`, so the panel may show no data. The "Re-generate with Prevention Plan" gate depends on this orphaned path.

**WebSocket streaming/abort is partial.** `ICPRouterOptions.server` (emitter/abort) is in the router signature but **consumed by no route body** in `icp-api-routes.ts`; even the "COMPLETE" convergence report self-flags streaming as partial (HTTP collects events into arrays rather than streaming; UI cancel button unwired). The legacy panel's WebSocket handlers exist but their end-to-end liveness is unverified.

**Latent / stub infrastructure.** `corpusHash` is hardcoded `'initial'` in `run()`, so `computeCorpusVersionDiff` cannot distinguish real corpus versions; `buildPolicyArchive` returns empty `policy_refs`; `computeCorpusVersionDiff` leaves `patches_applied`/`affected_quote_spans` empty; the OCR patch store is not wired into the live pipeline (staleness — including the doc-wide **circuit breaker** in `markCandidatesOnPatchCommit` — is latent); `scoreFacetAlignment` (ranking) and `checkAnchorRegression` (staleness) are explicit stubs; the Corpus Diff panel is an MVP placeholder requiring manually-typed run IDs; `PromptDecomposerConfig.interactive` exists but is unused inside `decompose()`.

**Read-only "trigger" stubs.** `POST /stress-test/:id` and `POST /generate/:id` do **not** perform work — they return existing session data or a "use the full pipeline" message. Real stress-testing/generation happen only inside a full run or `/adapter/generate`.

**Minor/unresolved.** `GET /adapter/config-defaults` returns its values wrapped in a `defaults` object, not bare. `/adapter/feedback` override-logging POSTs an empty body and swallows failures. `constrained-generator.ts` references `a.claim_text` while atoms elsewhere use `display_text`/`semantic_text` (possible optional field, not fully traced). The legacy panel reads `window._icpSessionId` but never sets it (latent coupling to external code). `prompt-builder-engine.buildPrompt` output is **not** consumed by `ConstrainedGenerator` (which builds its own per-paragraph prompts), and the briefs could not confirm where/whether `buildPrompt`'s result is threaded into `run()`. Whether the V2 frontend (`icp-panel-v2.js`) is actually mounted in the running dashboard was not verified by the source briefs (its handlers and controls were read in source).

## 7. Upgrading Source-Finding & Verification with Verbatim Ingestion + the Compiled Research Index

*This section addresses the specific request to factor in the newer verbatim-accurate ingestion (bbox / visual provenance) and the compiled research index. It is a focused deep-dive that deliberately re-examines the retrieval/verification seam from §2/§4/§6 through the lens of 'how would our current best-in-class source pipeline upgrade this,' and was produced + adversarially verified by a separate multi-agent workflow.*


### 7.A Current ICP Retrieval / Verification — and Its Limits

ICP finds and verifies sources in a four-stage seam inside `ICPOrchestrator` (`icp-orchestrator.ts`): Stage 2 `facetedRetrieval.retrieveForAllFacets` (L250) → Stage 3 `quoteRanker.canonicalizeAndRank` (L276) → Stage 4 `verifyQuotes` → `autoVerifier.verifyBatch` (L1175), with `StalenessEngine` running off-band on patch commits.

**Retrieval.** `FacetedRetrieval.retrieveForAllFacets(promptSpec, sourceScope, admissionPolicy)` iterates the prompt's required/optional facets, pulling per-facet terms from `promptSpec.retrieval_lexicon` (built in `prompt-decomposer.ts` / `llm-decomposition-provider.ts`, **not** from any canonical-term source). Each facet's query is assembled by `buildSemanticQuery(facet, retrievalTerms)` (faceted-retrieval.ts:354), which prefers a bare `facet.description` string — **no canonical-term expansion, no author/work injection**. It fans out per-collection `retrieval.hybridSearch(query, terms, {semantic:0.7, keyword:0.3}, {diversityBoost:true})` (L154) and slices to `maxChunks`. The only index-driven signal today is one layer down in `SmartRetrievalLayer` Step 4c (smart-retrieval-layer.ts:249–284): it loads `getCompiledIndex().canonicalTerms`, finds terms literally present in the query, and applies a **flat `CANONICAL_BOOST = 0.10`** to matching chunks. Author/work filtering exists only as the generic `whereFilter` in `RetrievalOptions`, which **ICP never populates**.

**Provenance.** `extractSpansFromChunk` (faceted-retrieval.ts:241) splits chunk text into sentences and admits *every* sentence (the `isRelevantToFacet` gate is defined but unused). Each `QuoteSpan` (icp-types.ts:309) carries fingerprints, `doc_id`, `page`, a `clean_text_range`, and a `source_anchor` synthesized as the **bare string `` `p. ${page_start}` ``** only when `page_start` exists (faceted-retrieval.ts:301 — repo-wide, the **single** write site for `source_anchor`). `buildProvenanceScorecard` (L390) sets `fidelity_score = chunk.relevanceScore` — a **retrieval score, not a text-match fidelity** — `ocr_risk_score` from a char heuristic `estimateOCRRisk`, and `doc_authority_tier` by string-matching `chunk.metadata.collection`.

**Verification.** `AutoVerifier.verify` runs Stage A (exact `cleanText.includes` → `normalized` → `approximateMatch` ≤10% edit → `match_type`) then Stage B signals (`exactness`, `ocr_risk_score`, `quote_length_factor`, `doc_authority_tier`, `canonical_overlap`, `anchor_confidence` flat 0.8/0.5), combined by `computeAutoConfidence` and thresholded in `determineStatus`.

**Limits (as documented in the briefs):**

- **Threshold tuned to weak corpus scores.** The effective `autoVerifyThreshold` is **0.65**, set in `icp-provider-factory.ts:103` (overriding the module default 0.85 in auto-verifier.ts:95), explicitly because "corpus relevance scores typically range 0.76–0.83, which would all be flagged at 0.85." Confidence leans on a **lowered relevance floor**, not on true verbatim proof.
- **No bbox-anchored exact verbatim.** `ContextChunk.metadata` already carries `has_bboxes`, `bboxes`, `source_method`, `clean_sha256` (retrieval/types.ts:154–170), but **none propagate into `QuoteSpan`** — dropped at `extractSpansFromChunk`. The anchor is a synthetic `p. N` string, not a coordinate. (Note: `bboxes` is declared as a **JSON *string*** at retrieval/types.ts:169–170, not a live array — any consumer must `JSON.parse` it first.)
- **No index-driven prioritization.** Query building never expands canonical terms/aliases or filters by author/work; `scoreFacetAlignment` in the ranker is an explicit **stub** (returns 0.7/0.5, quote-ranker.ts:385).
- **Stubbed staleness anchor check.** `checkAnchorRegression` returns `'ok'` unless `source_anchor` is absent (quote-span-staleness.ts:700–715; "Full anchor indexer integration is Phase 2").
- **~15% citation-coverage plateau** *(context from project memory; not independently re-derived in these briefs — a stated baseline, not verified here).*

### 7.B What the New Capabilities Add

**From verbatim-accurate ingestion:**

- **Exact verbatim matching with page + bbox anchors.** The ingestion cascade preserves both the exact character stream and its pixel location. `clean_corpus_text()` (run_ingest_phase2.py:546) is mirrored by `QuotationFidelityValidator.normalizeForLayout()`, so the same normalization that produced a stored chunk is reapplied at verify time. `classifyMatch` yields a `verbatim` tier at **raw ≥ 0.95** (quotation-fidelity-validator.ts:248). A `similarityScore` of 1.00 is a genuine text match rather than a relevance proxy — but note it is **case-insensitive by default** (`ignoreCase` defaults `true` — validator:133, applied at :641; the stage sets `ignoreCase:true` at :119), so a 1.00 score tolerates case/whitespace differences and is **not byte-identical**. Each chunk stores `bboxes` (per-page `{page_num, coords (super-box), blocks}`), `page_start`/`page_end`, and finest-grained chunk-level `locators` (Bekker/Stephanus references pinned to their own Marker block bbox + page).
- **Visual provenance.** `render_citation_bbox.py` produces a highlighted PNG of the source page in three modes — chunk-id mode; direct mode (`--pdf` / `--bboxes-json`, exposed as `renderBboxOverlayAsync`, used by the endnote generator); and quote-level mode (`find_fragment_bboxes`, difflib `SequenceMatcher` at 0.85, grouped into per-line rectangles, with a no-orphan-PNG guard at :272–274). `backfill-ku-bboxes.py` retro-enriches already-promoted Knowledge Units with the same `bboxes`/`source_method`. *(A stronger renderer, `highlight-page.py`, with a 6-strategy cascade exists but is **not yet unified** with the difflib quote mode — flagged.)*
- **OCR repair / quality signals.** `source_method` (`marker+bbox`, `pymupdf+bbox`, `layout_aware`, `ocr`, `pdftotext`, `text`) plus per-work `ocr_confidence`/`ocr_alerts` give a real provenance-quality signal to replace the char heuristic.

**From the compiled research index** (`compiled-index.json`, `builtAt` 2026-07-07; top-level keys `ontologyNodes`, `canonicalTerms`, `tensionEdges`, `crossPipelineHooks`: **542** `ontologyNodes`, **1442** `canonicalTerms`, **64** `tensionEdges`, **72** `crossPipelineHooks`):

- **Canonical-term query expansion.** `canonicalTerms` is sorted **length-descending for greedy longest-match** (`build_canonical_terms`, compile-corpus-index.py:1270); matching `ontologyNodes` supply `aliases`, `greek`, `transliteration`, `translation`, so retrieval fires on `energeia`/`weltarm` even when the draft uses an English gloss. (Verified node schema: `name`, `greek`, `transliteration`, `translation`, `definition`, `type`, `units`, `text`, `aliases`, `centralityTier` — **there is no `lines` field**.)
- **Author/work/tension-aware prioritization.** Each node's `text` (owning work) and `units[]` let ICP route toward the work that owns a concept and pull the primary source first. **Caveat:** `deduplicate_ontology_nodes` (compile script:1296–1298) merges same-named concepts across texts and joins their `text` with `'; '`, so a node's owning work is frequently a **multi-work string**, not a single routable work (e.g. the FCM node's `text` = `'Aristotle - Complete Works; Heidegger - The Fundamental Concepts of Metaphysics; Heidegger and Rhetoric'`) — the router must split and rank, not assume one value. A per-`text` node breakdown exists but is **only printed to stdout** by the compile script (lines 1364–1370); it is derivable by counting `node.text` but is **not a persisted `nodes-by-text` field**. `tensionEdges` (schema: `id`, `text`, `nodeA`, `nodeB`, `dependencyRelation`, `conflictRelation`, `description`, `units`) flag contested claims so both poles get cited.
- **Cross-pipeline hooks.** `crossPipelineHooks` (`sourceConcept→targetConcept`, `bridge`, `tag`) surface pre-vetted inter-work bridges with an `INTERP-high/med/low` confidence gate (58/8/6 respectively).
- **Citable § provenance for verification.** Node `definition` text carries embedded § provenance on **112 nodes** (e.g. `§42, p.176 / pdf 100`), giving the fidelity stages an approximate page/section target. (This is prose inside `definition`, **not** a structured `lines` or `locators` field — and the compiled index has **no `locators` field at all**; see §7.E.)

### 7.D New Capabilities Unlocked

- **Deterministic exact-verbatim citations (case-insensitive).** With ingestion's canonical `clean_text` served through `getCleanText` and normalization shared via `normalizeForLayout()`, Stage A `runStageA` returns `match_type: exact` for high-fidelity chunks — a `similarityScore` of 1.00 is a real text match, not a relevance proxy, though case/whitespace-insensitive rather than byte-identical (`ignoreCase` defaults true). `QuotationFidelityStage.autoFix()` then swaps a drafted quote toward its best-match `corpusText`, tightening (but not guaranteeing byte-exact) the drafted-vs-source string.
- **Bbox-highlighted provenance in the draft UI.** Every verified span can carry a `visualRefPath` (via `renderBboxOverlayAsync`) plus the parsed `bboxes` super-box/`blocks` and a chunk-level `locators` anchor — reviewers see the exact page region a quote came from, and canonical-citation anchors (Bekker/Stephanus) are pinned to a pixel box.
- **Index-driven "best source" selection.** Canonical-term expansion + `text`/`units`-aware `whereFilter` routing means the concept-owning primary work is retrieved first (e.g. "poor in world" → FCM `fcm-09/10/12`), honoring corpus-index-first — provided the router splits the `'; '`-joined multi-work `text` and ranks its candidates rather than filtering on the whole string.
- **Tension/debate-aware evidence balancing.** `tensionEdges` (`nodeA`/`nodeB`, `conflictRelation`, `dependencyRelation`) and per-work debate maps let the drafter detect a contested claim and cite both poles rather than flattening a live scholarly dispute; `crossPipelineHooks` add pre-vetted bridges gated by `INTERP-high/med/low`.
- **Safely raising the auto-verify threshold.** Once Stage B `anchor_confidence`, `canonical_overlap`, and `ocr_risk_score` draw on real bbox/index/OCR-quality signals rather than the relevance floor, a bbox-anchored, index-canonical span can be `auto_verified` on its own merits — allowing the effective threshold to climb back from **0.65 toward the module default 0.85** for high-fidelity sources without collapsing coverage, directly addressing the stated rationale at `icp-provider-factory.ts:103`.
- **Exact cross-extraction dedup.** Real `source_anchor`s make `canonicalize`'s anchor-first pass (`${doc_id}:${source_anchor}`) exact instead of colliding on coarse `p. N` strings.

### 7.E Risks / Caveats

- **Coverage vs. precision tradeoff.** Raising `autoVerifyThreshold` toward 0.85 improves precision but risks re-flagging borderline-but-valid quotes — the very reason it was lowered to 0.65. The threshold should rise **only for chunks with confirmed bbox / high-fidelity `source_method`**, kept conditional on the provenance signal, not applied globally.
- **`source_anchor` is a single-writer, many-reader coupling.** Repo-wide, `span.source_anchor` is written in exactly **one** place (faceted-retrieval.ts:301), which makes the "set it from a real Bekker/bbox locator" injection a clean single-point upstream change — but four downstream paths read it (`quote-ranker` `canonicalize` L113, staleness `checkAnchorRegression` L706, auto-verifier L331, `computeTrustTier` L423), so that one change **silently alters all four behaviors at once**. In particular the 0.8/0.5 anchor heuristic is hardcoded in **two** sites (auto-verifier.ts:330–333 **and** icp-types.ts:423); any "raise anchor_confidence when a bbox anchor exists" work must touch **both**, or the trust-tier badge will keep scoring a bbox-anchored span identically to a bare `p. N`.
- **Corpus-flip / degradation states.** Not all chunks carry provenance: Tier-3 ingestion (`pdftotext` / `marker_text_only`) sets `has_bboxes=False`, and project memory notes periods of "corpus 100% DEGRADED." Injection code must degrade gracefully — fall back to the current `p. N` anchor and relevance-based scoring when `bboxes`/`source_method` are absent, never assume every chunk has coordinates.
- **Locators/§ provenance live in the *chunks*, not the index.** The compiled index has **no `locators` field** and **no structured `lines` field**; its only citable provenance is the § text embedded in node `definition` (112 nodes). The rich Bekker/Stephanus `locators` (259 occurrences across `markdown_chunker.py`, `run_ingest_phase2.py`, `manifest.jsonl`) are an **ingestion-chunk/manifest** capability. Any plan that "sets `source_anchor` from a real locator" must read it from the chunk metadata / manifest, not from `compiled-index.json`.
- **Index staleness and leaky parsing.** `compiled-index.json` is a **pre-compiled snapshot** (`builtAt` 2026-07-07) rebuilt by `scripts/compile-corpus-index.py`; if the corpus is re-ingested it must be recompiled or routing goes stale. The header parser is **leaky**: several `centralityTier`/`type` values contain spilled markdown, so consumers must treat those as best-effort and rely on `name`, `definition`, `text`, `units` as load-bearing.
- **Renderer not yet unified.** Quote-level bbox location has two implementations — the live difflib `find_fragment_bboxes` (threshold 0.85) and the recommended-but-unmerged `highlight-page.py` 6-strategy cascade. A no-match yields no PNG (no orphan, guard at :272–274), so visual provenance is best-effort until unified.
- **Stubs are load-bearing.** `scoreFacetAlignment`, `checkAnchorRegression`, and `fidelity_score = relevanceScore` are named stubs; wiring the index/bbox signals into them is prerequisite work, not a config toggle — until then, ranking, staleness anchor-regression, and canonicalization gain nothing from the new capabilities.
- **OCR-repair guardrails.** `maybeRepairOCR` fires only above `ocrRepairThreshold 0.2` with a ≤15% divergence guard; seeding `ocr_risk_score` from ingestion `source_method` changes which spans trigger repair, so mis-mapped `source_method` values could either suppress needed repair or over-trigger vLLM calls.

The ~15% citation-coverage plateau is carried from project context as a stated baseline rather than re-derived; the `highlight-page.py`/difflib non-unification, index staleness, and leaky-header points are the briefs' own open caveats. Corrected against the compiled index's actual schema: no `lines`, no `locators`, no `provenance`, and no persisted `nodes-by-text` field.)*
