## What This Plan Does

Four things:

1. **Promote Tier 2 periodic scores to production** (hybrid: T2 continuous scores, T1 categorical labels) using a two-layer controller design.
2. **Re-enrich all active style profiles** with provenance metadata so every stored metric is traceable to its scoring regime.
3. **Verify explanation/advisory consistency** — ensure the hybrid score/label split doesn't produce contradictory messaging.
4. **Document the stable baseline** — formalize tier architecture using the two-layer model.

## Part 1: Two-Layer Controller Design

### Layer 1: Promotion Gate (AXIS_OVERRIDE_POLICY — retained)

The existing `AXIS_OVERRIDE_POLICY` is **kept as the gatekeeping layer**. It carries validation discipline that the ownership model does not replicate: minimum monotonicity advantage, genre-gating requirements, failure-bucket stability, and the explicit unlock criteria documented in Plan v2 A4.

An axis that has not passed promotion criteria cannot appear in the ownership layer with anything other than `scoreSource: 'tier1'`.

```typescript
// Layer 1: Promotion gate — decides WHETHER Tier 2 is eligible
// Retained from Plan v2 A4 with same unlock criteria:
//   1. Overall aggregate agreement AND monotonicity advantage
//   2. Per-genre slices where n >= 3 (hard gate)
//   3. Per-genre slices where n < 3 (manual-review watchlist)
//   4. Failure-bucket stability
const AXIS_OVERRIDE_POLICY: Record<string, AxisOverridePolicy> = {
  nounVerb:           { allowOverride: false, minMonotonicityAdvantage: 0 },
  parataxisHypotaxis: { allowOverride: false, minMonotonicityAdvantage: 0.05 },
  periodicRunning:    { allowOverride: true,  minMonotonicityAdvantage: 0 },  // PROMOTED: +0.130 mono validated
  voice:              { allowOverride: false, minMonotonicityAdvantage: 0 },
  primaryRegister:    { allowOverride: false, minMonotonicityAdvantage: 0 },
  opacity:            { allowOverride: false, minMonotonicityAdvantage: 0 },
};
```

### Layer 2: Merge Contract (AXIS_OWNERSHIP — new)

For axes that have passed the promotion gate, this layer specifies **what** Tier 2 provides. For axes that have not passed, all fields must be `'tier1'`.

```typescript
// Layer 2: Merge contract — decides WHAT Tier 2 provides for promoted axes
interface AxisOwnership {
  scoreSource: 'tier1' | 'tier2';
  labelSource: 'tier1' | 'tier2';
  confidenceSource: 'tier1' | 'tier2';
  explanationSource: 'tier1' | 'tier2' | 'label-aligned';
}

const AXIS_OWNERSHIP: Record<string, AxisOwnership> = {
  nounVerb:           { scoreSource: 'tier1', labelSource: 'tier1', confidenceSource: 'tier1', explanationSource: 'tier1' },
  parataxisHypotaxis: { scoreSource: 'tier1', labelSource: 'tier1', confidenceSource: 'tier1', explanationSource: 'tier1' },
  periodicRunning:    { scoreSource: 'tier2', labelSource: 'tier1', confidenceSource: 'tier1', explanationSource: 'label-aligned' },
  voice:              { scoreSource: 'tier1', labelSource: 'tier1', confidenceSource: 'tier1', explanationSource: 'tier1' },
  primaryRegister:    { scoreSource: 'tier1', labelSource: 'tier1', confidenceSource: 'tier1', explanationSource: 'tier1' },
  opacity:            { scoreSource: 'tier1', labelSource: 'tier1', confidenceSource: 'tier1', explanationSource: 'tier1' },
};
```

**Validation invariant:** For any axis where `AXIS_OVERRIDE_POLICY[axis].allowOverride === false`, all ownership fields must be `'tier1'`. The controller asserts this at construction time.

### Explanation consistency: `'label-aligned'` mode

The `explanationSource: 'label-aligned'` value means: the explanation is generated by whichever tier provides the label, using that tier's own score values. This prevents the inconsistency where T2's score (e.g., periodicRunningRatio = 0.75) would be quoted in an explanation while the label was derived from T1's score (e.g., "mixed" based on T1's 0.45).

**Implementation:** In `mergeWithPolicy()`, when `explanationSource === 'label-aligned'`:
- Keep Tier 1's explanation string for `periodicRunning` (it was generated by `deriveExplanations()` using Tier 1's own score)
- Do NOT regenerate the explanation using the merged (T2) score
- The merged metrics object has T2's `periodicRunningRatio` for numeric consumers but T1's `explanations.periodicRunning` for text consumers

This ensures that the label ("mixed"), the explanation ("Mixed sentence architecture with both periodic suspension and running delivery"), and the score for drift detection (0.479 from T2 ensemble) are each internally consistent within their own domain — labels/explanations agree with each other, and the score serves its own numeric purpose.

## Part 2: Profile Re-Enrichment with Provenance

### Provenance metadata

Add a `metricsProvenance` block to stored style profiles alongside `lanhamMetrics`:

```typescript
interface MetricsProvenance {
  analyzerVersion: string;       // e.g., "lanham-v2-phaseF"
  calibrationDate: string;       // ISO date
  scoreSourceByAxis: Record<string, 'tier1' | 'tier2'>;
  labelSourceByAxis: Record<string, 'tier1' | 'tier2'>;
  thresholdsApplied: string;     // e.g., "general-phaseF-calibrated"
}
```

The enrichment script writes this alongside `lanhamMetrics`:

```typescript
profile.metadata.metricsProvenance = {
  analyzerVersion: 'lanham-v2-phaseF-hybrid',
  calibrationDate: new Date().toISOString().split('T')[0],
  scoreSourceByAxis: {
    nounVerb: 'tier1', parataxisHypotaxis: 'tier1',
    periodicRunning: 'tier2',  // hybrid promotion
    voice: 'tier1', primaryRegister: 'tier1', opacity: 'tier1',
  },
  labelSourceByAxis: {
    nounVerb: 'tier1', parataxisHypotaxis: 'tier1',
    periodicRunning: 'tier1',  // labels from T1 even though scores from T2
    voice: 'tier1', primaryRegister: 'tier1', opacity: 'tier1',
  },
  thresholdsApplied: 'general-phaseF-calibrated',
};
```

This gives any later drift investigation full traceability: if a drift signal looks anomalous, you can check whether the profile and the generated text were scored under the same regime.

### Re-enrichment as rollout step

After the controller change is deployed, re-enrich **all** active style profiles immediately. This is mandatory, not optional — mixed baselines (old T1 periodic scores on some profiles, new T2 scores on others) create inconsistent drift detection.

### Regression check

Before and after re-enrichment, run the same sample text against the active profile:
1. Periodic drift advisory: does it change?
2. Periodic score delta (profile vs generated): does it change materially (>0.1)?
3. Explanation text: does it contradict the label?

If the drift advisory changes solely because of the score-source switch (not because the prose changed), the periodic drift thresholds may need adjustment for T2's score distribution. Document this as a follow-up if it occurs.
